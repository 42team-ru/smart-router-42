# Наборы настроек для сравнения

Гоняются так:

```
make bench-configs CONFIGS=config/examples/tuning
make bench-configs CONFIGS=config/examples/tuning LEVEL=compare_m ORACLE=1
```

## Что показал замер

На профиле `competitive` все конфиги ниже дают `competitive_ratio` 1.0 —
то есть работают на уровне офлайн-эталона, который считает задним числом по
всей очереди. Улучшать нечего: `count_share` уже упирается в потолок.

| конфиг | макс. доля | отклонение | ratio |
|---|---|---|---|
| `01_baseline` | 26.7% | 18.7 п.п. | 1.0 |
| `02_share_ceiling` | 25.3% | 18.7 | 1.0 |
| `03_budget_headroom` | 26.7% | 18.7 | 1.0 |
| `04_both_layers` | 25.3% | 18.7 | 1.0 |
| `05_volume_first` | 25.3% | 18.7 | 1.0 |
| `06_selector_mix` | 25.3% | 18.7 | 1.0 |

Слои дают выигрыш в доле лидера (25.3% против 26.7%) и не двигают отклонение.

Оставшиеся 18.7 п.п. — не промах роутера, а недостижимость: часть заявок не
подходит никому, у провайдеров кончаются дневные лимиты. Эталон с послезнанием
упирается в то же число.

## Где разница действительно есть

Между стратегиями, а не между настройками одной стратегии:

| стратегия | макс. доля | отклонение | ratio |
|---|---|---|---|
| `count_share`, `volume_share` | ~26% | 18.7 | 1.0 |
| `round_robin` | 19.3% | 18.7 | 1.0 |
| `priority`, `amount_range` | 90.3% | 68.3 | 3.65 |
| `conversion`, `load`, `obligations` | ~90% | 69–78 | 3.7–4.15 |

Стратегии из нижних строк не знают про целевые доли — они оптимизируют свою
цель и сваливают почти весь трафик одному провайдеру. Это не поломка, а их
устройство: `conversion` выбирает самого успешного, `load` — самого свободного.
