# П4 — офлайн-сравнение конфигураций в отчёте

## Зачем

Две дыры закрываются одной машинкой.

- Д-2: в боевом конфиге `layers: []`. Слои написаны, замерены (со слоями максимальное
  отклонение растёт с 5 до 25 п.п., competitive_ratio с 1.0 до 5.0) и выключены
  правильно, но жюри видит пустой список и читает критерий «согласование целей»
  (15 баллов) как ненаписанный. Числа сравнения должны лежать в отчёте, а не
  в комментарии к YAML.
- Д-6: `SCOPE.md` §4.7 обещает сравнение стратегий на одной очереди.

## Границы (инварианты, нарушить которые пакет не имеет права)

Сравнение — **постфактум**, ровно как офлайн-оптимум: результат попадает только
в отчёт и в консоль, никогда в принятие решений. Каждый вариант — такой же
**онлайн**-проход по очереди: заглядывание в будущие операции запрещено и здесь.
Порядок вариантов задаётся списком YAML, а не обходом хеша.

## Файлы

- `lib/offline/comparison.rb` — новый.
- `config/routing.yml` — новый ключ `comparison:` (список).
- `lib/config/schema_validator.rb`, `lib/config/schema_rules.rb`,
  `lib/config/routing_config.rb`, `lib/config/loader.rb` — новый ключ в схеме.
- `bin/route` — сборка секции и печать таблицы.
- `lib/reporting/report_builder.rb` — секция `comparison` (как `benchmark`: приходит
  готовым kwarg-ом, внутри не считается).
- `lib/reporting/console_summary.rb` — таблица.
- `README.md` — числа сравнения текстом.

## Конфиг

```yaml
comparison:
  - { name: round_robin,          strategy: round_robin, layers: [] }
  - { name: count_share,          strategy: count_share, layers: [] }
  - { name: count_share+layers,   strategy: count_share, layers: [budget_headroom, share_ceiling] }
```

Валидация: список отображений; `name` — непустая строка, уникальная;
`strategy` — известное имя (`Routing::Strategies.known`), иначе `SchemaError`
с перечислением известных; `layers` — список известных слоёв. Отсутствующий или
пустой ключ `comparison` — законный вход: секции в отчёте нет, поведение прежнее.

## Публичный интерфейс

```ruby
module Offline
  # Прогоняет ту же очередь под каждым вариантом на СВОЁМ состоянии и своём
  # экземпляре источника исходов (тот же seed). В принятие решений не входит.
  module Comparison
    # variants: [{name:, strategy:, layers:}], каждый элемент уже провалидирован конфигом
    # -> {"baseline" => String, "variants" => {name => metrics}, "note" => String}
    def self.build(variants:, operations:, providers:, config:, history:, baseline:)
  end
end
```

`metrics` каждого варианта — целочисленные счётчики и одно округлённое до 0.1 число:

```json
{"delivered": 10, "fallback_used": 0, "retried": 0,
 "max_deviation_pp": 0.0, "max_deviation_from_target_pp": 5.0}
```

- `delivered` — операции с `approved` или `expired` (`expired` считается условно
  успешным по ответу организаторов в QA);
- `fallback_used` — сколько операций ушло в `spacepayments`;
- `retried` — сколько операций имели больше одной реальной попытки
  (`decision == 'selected'`);
- `max_deviation_pp` — максимум модуля `distribution.*.deviation_pp` (от достижимого);
- `max_deviation_from_target_pp` — то же, но от паспортных целей; именно эта колонка
  сопоставима с `benchmark.max_deviation_pp`.

`baseline` — имя варианта, совпадающего с боевым конфигом (`strategy` и `layers`
из `config/routing.yml`). Если такого варианта в списке нет — `SchemaError` на старте:
таблица без опоры на фактический прогон бессмысленна.

## Готово когда

1. `make route` печатает таблицу из трёх строк с колонками
   `вариант | доставлено | fallback | ретраи | откл. от достижимого | откл. от цели`.
2. В `out/routing_report_test.json` есть `comparison.variants` с ровно теми именами,
   что в конфиге, и в том же порядке.
3. Совпадение с фактом: `comparison.variants[comparison.baseline].max_deviation_pp`
   равен максимуму модуля `distribution.*.deviation_pp` того же отчёта, а
   `delivered` — числу операций с `simulated_result` `approved`/`expired`
   в `routing_decisions_test.json`. Проверяется спеком, а не глазами.
4. Вариант со слоями и вариант без слоёв дают **разные** `max_deviation_pp`, и оба
   числа кодер выписывает в README после PASS раннера (не выдумывает заранее).
5. `diff out/routing_decisions_test.json routing_decisions_test.json` — пусто:
   сравнение не влияет на решения.
6. `make validate` → `Пройдено: 29`, `Ошибок: 0`, `Предупр.: 0`;
   `make gate` зелёный; `make determinism` → `детерминизм: OK`.
7. Конфиг без ключа `comparison` (например `config/examples/adwords.yml`) отрабатывает
   как раньше, секции в отчёте нет.

## Обязательные спеки

- `spec/offline/comparison_spec.rb`: два вызова подряд на одних входах дают
  идентичный результат; вариант с боевыми параметрами совпадает с метриками
  фактического прогона; порядок вариантов равен порядку в конфиге; каждый вариант
  получает свежее состояние (метрики варианта не зависят от того, каким по счёту
  он идёт в списке — проверить перестановкой списка);
  `round_robin` и `count_share` дают различимые метрики.
- `spec/config/...`: неизвестная стратегия/слой в `comparison` → `SchemaError`
  с понятным текстом; дублирующийся `name` → `SchemaError`; отсутствующий baseline
  → `SchemaError`; пустой/отсутствующий ключ — валиден.
- `spec/reporting/report_builder_spec.rb`: без kwarg-а `comparison` отчёт прежний
  (ключа нет); с kwarg-ом ключ на месте.
- `spec/bin/route_spec.rb`: таблица печатается; решения при включённом сравнении
  побайтово те же, что при выключенном.

## Что может сломаться молча

| Риск | Чем ловится |
|---|---|
| Вариант «наш» разъехался с фактическим прогоном (разный seed, порядок, состояние), и в отчёте две правды | п.3 приёмки + спек на совпадение с фактом |
| Прогон вариантов подтравливает боевое состояние (общий `State`, общий источник исходов с кэшем) | спек «метрики не зависят от порядка вариантов» + п.5 приёмки |
| Секция считается дважды (`ReportBuilder.build` в `bin/route` вызывается повторно для консоли) и удорожает прогон | сравнение считается один раз в `bin/route` и передаётся kwarg-ом, как `benchmark`; спек, что `ReportBuilder` внутри ничего не гоняет |
| Порядок вариантов зависит от обхода хеша | конфиг — список; спек на порядок |
| Сравнение случайно начинает влиять на решения | п.5 приёмки (побайтовый diff) |
