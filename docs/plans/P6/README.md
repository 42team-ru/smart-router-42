**Отдельное правило по П7.** Он единственный трогает решающий путь
(`lib/execution/executor.rb`) за сутки до сдачи. Если к моменту его старта до стопкода
остаётся меньше двух часов — не начинать. Порезанный П7 стоит одной фразы на защите;
недоделанный П7 в решающем пути стоит 40 баллов.

## Общее для всех пакетов

Кодеру брифы выдаются **по одному**. Готовность объявляет планировщик после PASS
от раннера; кодер этого права не имеет. FAIL — новый бриф с дословным выводом раннера.
Три FAIL подряд по одному пакету — стоп и эскалация человеку.

Проверка любого пакета — обе команды, обе обязаны быть зелёными:

```
make gate       # rspec + rubocop + отсутствие случайности
make validate   # ожидается: Пройдено: 29, Ошибок: 0, Предупр.: 0
```

Дополнительно там, где это указано в бриф: `make determinism` → `детерминизм: OK`.

## Инварианты, которые ни один пакет не имеет права нарушить

1. Детерминизм. В `lib/routing` и `lib/execution` нет `rand`, `shuffle`, `sample`,
   `Time.now`. Ловится `make gate` (цель `no-random`).
2. Целочисленная арифметика в решающем пути; дроби — перекрёстным умножением.
3. Причины отсева — дословно из `reference/data/reference_decisions.json`
   (`Routing::Reasons::SKIP`). Новых формулировок отсева не заводим.
4. `decision` в `attempts` — только `selected` / `skipped`.
5. `selected_provider` обязан входить в множество допустимых **по исходному снапшоту
   организаторов** `reference/data/providers.json`. Отсюда прямое следствие для П1/П2:
   поля, которые мы добавляем от себя, вправе только **сужать** наш пул и никогда его
   не расширять.
6. Онлайн-обработка: заглядывать в будущие операции очереди нельзя. Офлайн-расчёты
   (`lib/offline`, сравнение из П4) идут только в отчёт.
7. Резерв, а не пост-фактум: `approved` — коммит, `rejected` — полный откат,
   `expired` — резерв держится. Исключения вводятся только П2 (счётчик интенсивности)
   и обсуждаются в П7 (таймаут, продолжающий каскад) — оба описаны в своих брифах.
8. Причина без числа не принимается: каждый новый `details` содержит конкретное
   сравнение с числами.

## Детерминизм: где в этом плане могла бы завестись случайность

- **П3, round_robin.** Смещение ротации берётся из состояния прогона
  (`state.total_count_units`), а не из счётчика внутри объекта стратегии и не из времени.
  Порядок кандидатов перед ротацией фиксируется сортировкой по имени.
- **П4, порядок вариантов.** Варианты сравнения читаются из YAML-**списка**, а не из
  отображения: порядок обхода хеша в вывод не попадает.
- **П1, сообщение об ошибке override.** Список неизвестных провайдеров в тексте
  исключения сортируется, иначе текст зависит от порядка ключей YAML.
- **П2, счётчик минут.** Ключ — `[имя провайдера, created_at[0,16]]`; значение растёт
  только в `reserve`. Никаких «текущих минут» из системных часов.
- **П7, ветвление каскада.** Режимы выбираются строковыми значениями конфига,
  сравнение — по символу, без `respond_to?`-магии и без порядка ключей хеша.

## Развилки: решения человека

Все пять развилок закрыты **2026-09-05**. Ниже — статус, выбранный вариант и что
из этого следует для пакетов.

**Ф-1 (Д-3a). Исчерпание каскада.**
Статус: **решено 2026-09-05 → вариант B** (переключатель конфига, по умолчанию —
сегодняшнее поведение `last_candidate`).
ТЗ: «при отказе/таймауте — исключить провайдера из пула и выбрать следующего. Если пул
пуст — fallback на spacepayments». У нас (`lib/execution/executor.rb:59`) исчерпанный
каскад даёт `selected` = последний реальный кандидат с `result: rejected`; spacepayments
подхватывает только пустой по допуску пул. Человек выбрал не «оставить и защититься
словами», а «сделать обе трактовки доступными переключателем, дефолт не меняя».
Следствие: новый пакет **П7**; в README защиты формулировка меняется с «мы читаем ТЗ
так» на «доступны обе трактовки, по умолчанию такая-то, вот почему».
Планировщик рекомендовал вариант A; решение человека принято и зафиксировано.

**Ф-2 (Д-3b). `expired` обрывает каскад.**
Статус: **решено 2026-09-05 → вариант B** (переключатель конфига, по умолчанию —
сегодняшнее поведение «таймаут каскад не продолжает»).
Опора дефолта — ответ организаторов в QA дословно: «когда мы получаем тайм-аут, мы
точно не знаем, что у нас там произошло. Поэтому пока что мы считаем, что у нас как бы
всё хорошо прошло». Альтернативная ветка вступает в прямое противоречие
с `lib/execution/pending_resolver.rb` (резерв держится и одновременно идёт следующая
попытка) — разрешение противоречия описано в брифе **П7**, пункт 5, и обязано быть
проговорено на защите, а не спрятано в коде.

**Ф-3 (Д-1). Где живёт наш расширенный снапшот.**
Статус: **решено 2026-09-05 → вариант B** — пристинный `reference/data/providers.json`
не трогаем, наш снапшот `data/providers.json`, дефолт `--providers` в `bin/route`
указывает на него. Зелёный `make validate` доказывает ровно то свойство, которое
проверят в час стопкода: наши решения допустимы по снапшоту организаторов.
Изменений в брифе П1 не требуется — вариант B там и заложен.

**Ф-4 (Д-1b/П2). Строгость rate-limit-фильтра.**
Статус: **решено 2026-09-05 → вариант B** — фильтр применяется, только если после него
остаётся хотя бы один внешний кандидат. Изменений в механике П2 не требуется.
Дополнительно: смягчение — **наше решение до ответа экспертов**, а не окончательная
трактовка ТЗ. Вопрос выписан организаторам в `docs/QUESTIONS_FOR_EXPERTS.md`, В-1
(интенсивность) и В-2 (fallback при исчерпании каскада и таймауте); бриф П2 обязан
сослаться на этот файл, чтобы на чекпоинте вопрос был задан, а не забыт.

**Ф-5 (Д-2). Включать ли слои в боевом прогоне.**
Статус: **решено 2026-09-05 → вариант A** — `layers: []` в боевом конфиге остаётся,
сравнение «со слоями / без слоёв» с числами идёт в отчёт и README (П4).
Замерено: со слоями максимальное отклонение растёт с 5 до 25 п.п., competitive_ratio
с 1.0 до 5.0 — то есть выключены они правильно, и это надо показать числами,
а не умолчанием.
