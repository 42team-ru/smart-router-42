# П2 — интенсивность: счётчик, безопасное правило, значения снапшота

## Зачем и что сейчас не так

`Routing::Constraints::RateLimit` написан и покрыт спеком, но на боевых данных мёртв
дважды: в снапшоте нет `requests_per_minute_limit`, а `State::Providers` не отвечает
на `requests_in_minute` — `RateLimit.violation` возвращает `nil` по обеим причинам.
То есть «Интенсивность» из hard-таблицы ТЗ сегодня не работает вообще.

## Решение, которое кодируется (решено человеком 2026-09-05, развилка Ф-4, вариант B)

Rate limit остаётся hard-фильтром, но с явным правилом разрешения конфликта:
**ограничение по интенсивности не применяется, если после его применения не остаётся
ни одного внешнего кандидата.** Причина — валидатор организаторов интенсивности
не знает: наш отсев может только разойтись с эталоном, и цена расхождения — провал
детерминированного кейса, то есть 20 баллов. Неприменение фиксируется в `details`
с числами, а не замалчивается.

## Это наше решение, а не окончательная трактовка ТЗ

Смягчение hard-фильтра — компромисс, принятый **до ответа экспертов**. Вопрос уже
выписан организаторам: `docs/QUESTIONS_FOR_EXPERTS.md`, В-1 (интенсивность как
hard-constraint) и В-2 (fallback при исчерпании каскада и таймауте). Требования
к пакету:

1. Комментарий над правилом неприменения в `lib/routing/planner.rb` ссылается на В-1
   из `docs/QUESTIONS_FOR_EXPERTS.md` — чтобы при ответе экспертов было видно, что
   именно менять.
2. Раздел README из П5 называет это нашим решением до ответа, а не трактовкой ТЗ.
3. Если эксперты ответят «фильтр строгий» до стопкода — правило неприменения
   снимается одной правкой в `Planner`, спек плотной очереди при этом обязан
   сообщить об изменении поведения, а не промолчать.

## Файлы

- `data/providers.json` — добавить `requests_per_minute_limit`.
- `lib/state/providers.rb` — счётчик запросов по минутам.
- `lib/routing/planner.rb` — отдельный этап rate limit после базового отсева.
- `lib/routing/constraints.rb` — `RateLimit` уходит из `REGISTRY` в отдельную
  константу/этап; `Constraints.check`/`eligible?` при `state == nil` обязаны вести себя
  ровно как сегодня (иначе поедут `Routing::Achievable` и `eligibility_for` в отчёте).
- `README.md` — раздел про правило неприменения.

## Значения

| провайдер | requests_per_minute_limit |
|---|---|
| vipay | 7 |
| payflow | 10 |
| quickpay | 15 |
| spacepayments | null |

7 и 15 — дословно из ТЗ («не более 7 заявок/мин на терминал A, 15/мин на терминал B»),
10 на payflow — середина, чтобы правило было различимо на плотной очереди.

## Публичный интерфейс

```ruby
class State::Providers
  # Сколько запросов уже отправлено провайдеру в эту минуту.
  # minute — строка вида "2026-07-30T09:05" (operation.created_at[0, 16]).
  def requests_in_minute(name, minute) # -> Integer
end
```

Правила счётчика:

1. Растёт **только** в `reserve` — по факту отправки запроса, ключ
   `[имя провайдера, operation.created_at[0, 16]]`. Fallback-резерв тоже считается.
2. **Не уменьшается** ни в `rollback`, ни в `hold`, ни в `commit`: интенсивность —
   это отправленные запросы, а не занятая ёмкость. Это единственное сознательное
   отступление от правила «rejected — полный откат», и оно относится к счётчику
   интенсивности, а не к резерву; отразить комментарием в коде.
3. Счётчик живёт внутри экземпляра `State::Providers`. Новый экземпляр — чистый счётчик
   (это требование П4: каждый вариант сравнения гоняется на своём состоянии).
4. `Time.now` не появляется: минута берётся из `created_at` операции.

Правило неприменения в `Planner#plan`:

- сначала базовый отсев (как сейчас, без `RateLimit`) → `candidates`, `skipped`;
- затем `RateLimit` применяется к `candidates`: если после отсева остаётся ≥ 1 кандидат,
  отсеянные уходят в `skipped` с `reason: 'rate_limit_exceeded'` и уже существующим
  форматом `details`;
- если не остаётся ни одного — `candidates` остаётся прежним, и в
  `PlanTrace`-сегмент добавляется строка с числами вида
  `rate_limit: vipay 7/7 достигнут, ограничение не применено — других допустимых нет`.
  Формулировка `reason` при этом **не изобретается**: попытка остаётся обычной
  `selected` с прежними `reason`, новая строка живёт только в `details`.

## Готово когда

1. Публичная очередь не меняется: `diff out/routing_decisions_test.json routing_decisions_test.json`
   — пусто (в очереди максимум 2 операции в минуту, ни один лимит не достигается).
2. `make validate` → `Пройдено: 29`, `Ошибок: 0`, `Предупр.: 0`.
3. `bundle exec bin/route reference/data/operations_queue_10.json 2>&1 | grep -c 'правило не применяется'`
   → `0`.
4. Новый спек плотной очереди зелёный (см. ниже).
5. `make gate` зелёный, `make determinism` → `детерминизм: OK`.

## Обязательные спеки

- `spec/fixtures/queues/dense_minute.json` — 10 операций с одинаковой минутой
  `created_at` (секунды разные), суммы и банки как в публичной очереди, чтобы четыре
  детерминированных кейса сохранились.
- `spec/routing/rate_limit_pipeline_spec.rb`:
  1. на плотной очереди в `skip_reasons` отчёта появляется `rate_limit_exceeded` ≥ 1
     (иначе правило снова мертво, и спек это ловит);
  2. **каждый** `selected_provider` входит в множество допустимых, посчитанное
     по пристинному `reference/data/providers.json` копией логики
     `eligible_providers` из `reference/scripts/validate_10.rb`;
  3. все четыре кейса из `reference_decisions.json` дают `required_provider`;
  4. хотя бы в одном решении сработало правило неприменения — и в `details` этой
     попытки есть числа лимита.
- `spec/state/providers_spec.rb` (дополнить): счётчик растёт на `reserve`; не падает
  на `rollback`/`hold`/`commit`; разные минуты не смешиваются; новый экземпляр
  `State::Providers` начинает с нуля.
- `spec/routing/constraints/rate_limit_spec.rb` (дополнить): при `state == nil`
  нарушения нет; `Routing::Constraints.eligible?(provider, operation)` без состояния
  даёт те же ответы, что до пакета (защита `Achievable` и отчёта).

## Что может сломаться молча

| Риск | Чем ловится |
|---|---|
| Правило неприменения срабатывает всегда, и фильтр де-факто выключен | пункт 1 спека плотной очереди (`rate_limit_exceeded` обязан появиться) |
| Фильтр выбивает провайдера из детерминированного кейса | пункт 3 спека плотной очереди |
| Наш пул расширился относительно валидаторского | пункт 2 спека плотной очереди |
| `RateLimit` начал влиять на `Routing::Achievable` и `deviation_pp` поехал | спек «без состояния поведение прежнее» + неизменность отчёта на публичной очереди |
| Счётчик минут протёк между вариантами сравнения (П4) | спек «новый экземпляр начинает с нуля» |
| `created_at` в тестовой очереди без секунд/в другом формате — срез `[0, 16]` даёт мусор | спек на нестандартный `created_at` в `spec/boundary_cases_spec.rb`: срез не должен ронять прогон |
