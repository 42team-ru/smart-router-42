# П7 — настраиваемый fallback: исчерпание каскада и таймаут

## Зачем

ТЗ: «при отказе/**таймауте** — исключить провайдера из пула и выбрать следующего.
Если пул пуст — fallback на spacepayments». Наше поведение отличается дважды:

- исчерпанный каскад оставляет `selected_provider` = последний реальный кандидат
  с `result: rejected` (`lib/execution/executor.rb:59`), spacepayments подхватывает
  только пул, пустой **по допуску**;
- `expired` каскад не продолжает: резерв держится, операция считается условно успешной.

Человек решил (2026-09-05, развилки Ф-1 и Ф-2, вариант B): обе трактовки должны быть
доступны **переключателем конфига**, а поведение по умолчанию остаётся сегодняшним.
Это ровно тот аргумент, который жюри проверяет в критерии «параметры правил можно
изменять через настройки без изменения основной логики», и одновременно снятие
претензии «вы не выполнили пункт ТЗ».

## Границы

Дефолты обязаны воспроизводить сегодняшнее поведение **побайтово**. Это критерий
приёмки, а не пожелание: если дефолтный прогон изменил хоть один символ
`routing_decisions_test.json` — пакет не сделан, независимо от красоты кода.

Инварианты, которые пакет обязан оставить нетронутыми (проверяются явно, см. приёмку):
`decision` только `selected`/`skipped`; `selected_provider` из множества допустимых
по пристинному снапшоту; резерв/коммит/откат/hold по правилам `State::Providers`;
никаких `rand`/`shuffle`/`sample`/`Time.now` в `lib/execution`; причины отсева
дословные.

## Файлы

- `config/routing.yml` — новый ключ `cascade` с дефолтами, записанными явно.
- `lib/config/schema_validator.rb`, `lib/config/schema_rules.rb`,
  `lib/config/routing_config.rb`, `lib/config/loader.rb` — новый ключ в схеме.
- `lib/execution/executor.rb` — два режима.
- `lib/routing/reasons.rb` — одна новая причина **выбора** (не отсева).
- `bin/route` — прокидывание режимов в `Execution::Executor`.
- `config/examples/tz_literal.yml` — новый пример: обе альтернативные ветки включены.
- `README.md` §4 — таблица конфигурации.

## Конфиг

```yaml
cascade:
  exhausted: last_candidate   # last_candidate (по умолчанию) | fallback_provider
  on_timeout: stop            # stop (по умолчанию) | continue
```

Валидация: `cascade` — отображение; неизвестный ключ внутри → `SchemaError`
с перечислением допустимых; значение вне перечисления → `SchemaError` вида
`cascade.exhausted должен быть одним из: last_candidate, fallback_provider; получено "foo"`.
Отсутствующий ключ `cascade` целиком и отсутствующие подключи — законный вход,
подставляются дефолты. Конфиги в `config/examples/*.yml` без этого ключа обязаны
работать как раньше.

## Поведение

```ruby
Execution::Executor.new(outcomes:, exhausted: :last_candidate, on_timeout: :stop)
```

Режимы приходят символами, собираются в `bin/route` из конфига; кода-дефолта, кроме
значений kwarg-ов, нет.

**`exhausted: :last_candidate`** (дефолт) — как сегодня: после исчерпания каскада
`Outcome` содержит `selected` = последний кандидат, `result: :rejected`, новых попыток
нет.

**`exhausted: :fallback_provider`** — после исчерпания каскада выполняется ещё одна
попытка на `state.fallback`: `reserve` → `@outcomes.call(operation, fallback, N+1)` →
`attempt` → переход состояния по исходу (та же `apply_state_transition`, что
в `run_fallback`). Попытка пишется как `decision: 'selected'` с **новой** причиной
выбора `fallback_after_cascade` (добавить в `Routing::Reasons::SELECTED`; список причин
**отсева** не трогаем — он дословный) и `details` с числами:
`3 кандидата отказали из 3, каскад исчерпан`.

**`on_timeout: :stop`** (дефолт) — как сегодня: `state.hold`, каскад завершён,
`result: :expired`.

**`on_timeout: :continue`** — `state.hold` **выполняется всё равно** (резерв держится,
это инвариант), после чего цикл идёт к следующему кандидату. Итог:

- если следующий кандидат дал `approved` — `selected` = он, `result: :approved`;
- если все последующие дали `rejected` и каскад исчерпан — `selected` = **провайдер,
  на котором был таймаут**, `result: :expired` (он условно успешен; выбирается
  первый по порядку таймаут, если их было несколько). Правило `exhausted` в этом случае
  **не применяется**: каскад не пуст по исходам, у нас есть условно успешная попытка.
  Это правило должно быть записано комментарием в коде — иначе оно выглядит
  случайностью.

## Пункт 5 — противоречие с `PendingResolver`, назвать прямо

При `on_timeout: :continue` по одной операции одновременно существуют: удержанный
резерв на первом провайдере (`State#hold`, ждёт поздний статус-чек) и новая попытка
на втором. В модели это двойная выплата.

Разрешение в коде: резерв **не освобождается** (освободить его без статус-чека —
нарушить инвариант и соврать в счётчиках); ответственность за схлопывание остаётся
на `Execution::PendingResolver#resolve`, который применит настоящий ответ как
компенсирующую delta. То есть режим `continue` честно моделирует «мы рискнули отправить
второй раз, не дождавшись ответа», а не «мы забыли про первый».

Что говорится жюри (одна фраза, попадает в README из П5): «в режиме по умолчанию мы
не дублируем выплату при таймауте — держим резерв и ждём статус-чек, как ответили
организаторы в Q&A; буквальный режим ТЗ доступен ключом конфига, и мы показываем,
чем именно за него платим — риском двойной отправки».

## Пункт 3 — цена альтернативной ветки, зафиксировать числом

Кодер обязан прогнать публичную очередь во **всех четырёх** комбинациях и записать
фактический вердикт валидатора в таблицу — сначала в этот бриф (раздел «Замеры»),
затем одной строкой в README из П5:

| `exhausted` | `on_timeout` | `Ошибок:` | что именно ломается |
|---|---|---|---|
| last_candidate | stop | 0 (дефолт) | — |
| fallback_provider | stop | 0 | — (ветка не срабатывает: на публичной очереди нет `rejected`-исчерпания) |
| last_candidate | continue | 0 | — (ветка не срабатывает: единственный `expired`-кандидат — последний в каскаде) |
| fallback_provider | continue | 0 | — (обе ветки не срабатывают одновременно, см. ниже) |

Команды замера (для каждой комбинации свой временный конфиг, производный от
`config/routing.yml` заменой `exhausted`/`on_timeout`):

```
bundle exec bin/route reference/data/operations_queue_10.json --config <cfg> --out-dir /tmp/p7
ruby reference/scripts/validate_10.rb /tmp/p7/routing_decisions_test.json
```

Фактический замер (2026-09-05, seed 42, `reference/data/operations_queue_10.json`,
`reference/scripts/validate_10.rb`): все четыре комбинации дают **`Пройдено: 29,
Ошибок: 0, Предупр.: 0`**, и `routing_decisions_test.json` во всех четырёх
комбинациях побайтово идентичен (`diff` пустой). Гипотеза планировщика **опровергнута
числом**, а не подтверждена: она была верна в первой половине (на seed 42 публичная
очередь действительно не содержит ни одного `rejected`, ветка `exhausted` неактивна)
и неверна во второй. Причина: `op_103` и `op_104` дают `expired` на `quickpay`, и
`quickpay` — единственный кандидат в каскаде (`total_candidates == 1`). Правило
`on_timeout: :continue` в `Executor#run_cascade` держит резерв и пытается перейти
к следующему кандидату, но следующего нет — цикл заканчивается естественно, попадает
в `cascade_exhausted`, где `expired_provider` уже установлен на `quickpay`, и правило
`exhausted` явно не применяется (см. комментарий в `lib/execution/executor.rb`).
Итог для этой пары операций при `continue` побайтово совпадает с `stop`: `selected =
quickpay`, `result: :expired`, `spacepayments` не подключается. Комбинация `continue`
+ `fallback_provider` уходит в `spacepayments` только если каскад состоит из ≥2
кандидатов и все реальные попытки отказали или протаймаутили без approved — на
публичной очереди такого кейса нет, поэтому обе альтернативные ветки на seed 42
остаются наблюдаемо латентными (код исполняется, наблюдаемый результат не меняется).
Следствие: `config/examples/tz_literal.yml` предупреждения "не для сдачи" не несёт —
он безопасен и на публичной очереди, но это свойство данных, а не гарантия кода:
на другой очереди с настоящим `rejected`-исчерпанием или с `expired` не на последнем
кандидате обе ветки дадут другой результат по конструкции.

## Готово когда

1. **Побайтовая неизменность дефолта**: после `make route`
   `diff out/routing_decisions_test.json routing_decisions_test.json` — пусто;
   `diff` секций отчёта, кроме заведомо изменившихся П4-полей, — пусто.
2. `make validate` → `Пройдено: 29`, `Ошибок: 0`, `Предупр.: 0`.
3. `make gate` зелёный; `make determinism` → `детерминизм: OK`.
4. `bash scripts/check_determinism.sh` проходит (в `lib/execution` не появилось
   источников случайности).
5. Таблица «Замеры» заполнена фактическими числами из вывода валидатора, а не
   ожиданиями; для каждой ненулевой строки названа конкретная операция и провайдер.
6. `config/examples/tz_literal.yml` запускается и отрабатывает без исключений.
7. Конфиг с опечаткой в значении (`exhausted: fallback`) даёт сообщение и код 1
   без трейса.

## Обязательные спеки

- `spec/execution/executor_spec.rb` (дополнить):
  - `exhausted: :last_candidate` — все кандидаты отказали → `selected` = последний,
    `result: :rejected`, попыток ровно столько же, сколько кандидатов (регресс-защита
    сегодняшнего поведения);
  - `exhausted: :fallback_provider` — все отказали → добавляется попытка
    на `spacepayments` с `decision: 'selected'`, `reason: 'fallback_after_cascade'`,
    `details` с числами; `attempt_no` продолжает нумерацию;
  - `on_timeout: :stop` — `expired` завершает каскад, `state.hold` вызван один раз;
  - `on_timeout: :continue` — `expired` держит резерв **и** каскад продолжается;
    при последующем `approved` `selected` = второй провайдер, `result: :approved`,
    а held-резерв первого остался (проверить через `State::Providers`, а не через
    моки: `resolve_hold` обязан отработать, значит резерв на месте);
  - `on_timeout: :continue` + все последующие `rejected` → `selected` = провайдер
    с таймаутом, `result: :expired`;
  - во всех ветках каждое `attempt.decision` ∈ `%w[selected skipped]`.
- `spec/config/...`: дефолты при отсутствующем `cascade`; `SchemaError` на неизвестном
  подключе и на значении вне перечисления; существующие `config/examples/*.yml`
  грузятся без изменений.
- `spec/bin/route_spec.rb` (дополнить): режимы доезжают из конфига в `Executor`
  (проверять по наблюдаемому поведению на подготовленном конфиге, не по внутренностям);
  дефолтный прогон печатает и пишет ровно то же, что до пакета.
- `spec/routing/reasons_spec.rb` или существующий контрактный спек: `SKIP` не изменился
  (список отсева остаётся дословным), `SELECTED` пополнился ровно одной причиной.

## Что может сломаться молча

| Риск | Чем ловится |
|---|---|
| Дефолт незаметно поехал (другой порядок попыток, лишний attempt, другой `result`) | п.1 приёмки — побайтовый diff — плюс регресс-спеки на обе ветки дефолта |
| В режиме `continue` резерв тихо освобождается, и `in_progress` расходится с реальностью | спек на held-резерв через `State::Providers#resolve_hold` |
| Новая причина попала в `SKIP` и разошлась с эталонным файлом | спек «`SKIP` не изменился» |
| Fallback-попытка не обновила состояние (нет `reserve`/перехода) | спек на `exhausted: :fallback_provider` со счётчиками состояния до и после |
| Альтернативная ветка тихо включена в боевом конфиге в час стопкода | дефолты записаны в `config/routing.yml` явно, а не подразумеваются; п.2 приёмки — `make validate` на боевом конфиге |
| Ветка ломает валидатор, но цена нигде не записана | п.5 приёмки: таблица «Замеры» с числами и именами операций |
