# П5 — пакет защиты в README

## Зачем

Три дыры бьют в одно место — в то, что жюри читает глазами, а не запускает.

- Д-3: наше поведение каскада расходится с буквой ТЗ. Расхождение обязано быть
  **названным, обоснованным и переключаемым** (решения человека 2026-09-05 — развилки
  Ф-1 и Ф-2 в `README.md` этой папки: по обеим принят вариант B, переключатель конфига
  с сегодняшним поведением по умолчанию; сам переключатель делает П7).
- Д-5: из четырёх обязательных ссылок задачи D-2 в README есть только AdWords.
- Д-7: `decision: "selected"` у отказавшего провайдера и два разных «отклонения»
  в отчёте выглядят как небрежность, пока не объяснены одной фразой.

Код в этом пакете не меняется — кроме одного спека, который держит README честным.
П5 выполняется **после П7**: числа цены альтернативной ветки берутся из его замеров.

## Файлы

- `README.md` — четыре новых подраздела и правка §7.
- `spec/bin/retry_demo_spec.rb` — новый.

## Содержание разделов

**1. «Fallback и каскад: две трактовки, обе доступны».** Раздел переписывается
относительно первой редакции этого брифа: человек решил 2026-09-05 (развилки Ф-1
и Ф-2, вариант B), что обе трактовки должны быть доступны переключателем конфига,
а поведение по умолчанию остаётся нашим. Поэтому формулировка не «мы читаем ТЗ так»,
а «доступны обе, по умолчанию такая-то, вот почему и вот чем платит вторая».
Структура раздела:
1) дословная цитата ТЗ («при отказе/таймауте — исключить провайдера из пула и выбрать
   следующего. Если пул пуст — fallback на spacepayments»);
2) поведение по умолчанию: spacepayments — fallback **по допуску** (ни один внешний
   провайдер не прошёл hard-constraints), исчерпание каскада оставляет
   `selected_provider` = последний реальный кандидат с `result: rejected`; таймаут
   каскад не продолжает, резерв держится, поздний ответ применяет
   `lib/execution/pending_resolver.rb`;
3) три опоры дефолта с адресами: `reference/QA_TRANSCRIPT.txt:84` («если hard-фильтр
   никто не прошёл, то там есть fallback на дефолтный провайдер space payments»),
   ответ организаторов про таймаут дословно («когда мы получаем тайм-аут, мы точно
   не знаем, что у нас там произошло. Поэтому пока что мы считаем, что у нас как бы
   всё хорошо прошло»), эталонные кейсы `reference/data/reference_decisions.json`;
4) переключатель: ключ `cascade` (`exhausted`, `on_timeout`) из П7, пример
   `config/examples/tz_literal.yml`, одна команда запуска;
5) **цена буквальной ветки числом** — строка из таблицы «Замеры» брифа П7:
   сколько ошибок даёт валидатор на публичной очереди при включённых альтернативных
   режимах и на каких операциях. Если цена ненулевая, README обязан прямо сказать,
   что в боевом прогоне этот режим не используется, и почему;
6) фраза про риск двойной отправки в режиме `on_timeout: continue` (готовая
   формулировка — в брифе П7, пункт 5).

**2. «Почему у отказавшего провайдера `decision: "selected"`».** Это ограничение схемы
организаторов: `reference/scripts/validate_10.rb:62-64` считает ошибкой структуры любое
значение, кроме `selected` и `skipped`. Наша семантика неудачной попытки кодируется
дополнительными полями `result` и `attempt_no` — их валидатор игнорирует, а человек
читает. Формулировка должна прямо говорить: это не наша семантика, а контракт проверки.

**3. «Два отклонения — и почему они разные».** `distribution.deviation_pp` — отклонение
от **достижимой** доли (`Routing::Achievable`, квантование на десяти заявках и
физические ограничения очереди), `benchmark.max_deviation_pp` — отклонение
от **паспортных** целей 40/35/25, потому что офлайн-эталон сравнивается с целями,
а не с потолком. Привести оба числа фактического прогона (сегодня 0.0 и 5.0) и одну
фразу «одно меряет качество движка, второе — цену недостижимости целей».
Проверить формулировку вопросом жюри: «а какое из двух настоящее?» — ответ должен
быть в тексте, а не в голове докладчика.

**4. «Алгоритмы и источники».** Четыре ссылки, у каждой — файл, где алгоритм живёт:

| Алгоритм | Источник | Где в коде |
|---|---|---|
| Метод Сент-Лагю (дивизорный аллокатор долей) | Balinski, Young. *Fair Representation: Meeting the Ideal of One Man, One Vote*, 2-е изд., Brookings, 2001 | `lib/routing/strategies/count_share.rb`, `lib/routing/share_ledger.rb` |
| Deficit Round Robin | Shreedhar, Varghese. *Efficient Fair Queueing Using Deficit Round Robin*, IEEE/ACM Transactions on Networking 4(3), 1996, doi:10.1109/90.502236 | `lib/routing/strategies/*` (долговой аллокатор), `lib/routing/strategies/round_robin.rb` |
| AdWords / BALANCE | Mehta, Saberi, Vazirani, Vazirani. *AdWords and Generalized Online Matching*, FOCS 2005, doi:10.1109/FOCS.2005.21 | `lib/routing/layers/budget_headroom.rb` |
| Лексикографическое goal programming | Charnes, Cooper. *Management Models and Industrial Applications of Linear Programming*, Wiley, 1961; Ignizio. *Generalized goal programming*, Computers & Operations Research 10(4), 1983 | `lib/routing/layer_stack.rb`, `lib/routing/layers/share_ceiling.rb` |

Кодер обязан сверить, что названный файл действительно реализует названный алгоритм,
и, если нет, — доложить расхождение, а не подгонять таблицу.

**5. «Демо ретрая».** На боевом seed 42 публичная очередь не содержит ни одного
`rejected`: жюри не увидит ни повторной попытки, ни `next_in_cascade` — а это
4 балла экспертов и 2 балла техжюри («последовательность действий при отказе»).
Нужна одна команда в README, детерминированно показывающая каскад:
`bundle exec bin/route reference/data/operations_queue_10.json --seed <N> --out-dir /tmp/retry`.
`N` кодер подбирает перебором `1..99` в порядке возрастания, берёт **первое** значение,
при котором в решениях появляется `reason: "next_in_cascade"`, и фиксирует это число
и в README, и в спеке. Рядом — вывод одной операции с двумя попытками.

## Готово когда

1. `grep -c -e 'Sainte' -e 'Сент-Лагю' README.md`, `grep -c 'Deficit Round Robin' README.md`,
   `grep -c 'FOCS 2005' README.md`, `grep -c 'goal programming' README.md` — каждый ≥ 1.
2. В README есть все четыре подраздела (1-3 и 5 выше) — проверяется глазами раннера
   по заголовкам, перечисленным в этом брифе.
3. Команда демо ретрая из README, запущенная как есть, даёт
   `grep -c next_in_cascade /tmp/retry/routing_decisions_test.json` ≥ 1.
4. Если П7 сделан: в README есть строка про переключатель `cascade` и **число** цены
   альтернативной ветки, совпадающее с таблицей «Замеры» брифа П7 (сверяется глазами
   раннера по двум файлам).
5. `make gate` и `make validate` зелёные; боевые файлы не изменились:
   `diff out/routing_decisions_test.json routing_decisions_test.json` — пусто.

## Обязательные спеки

- `spec/bin/retry_demo_spec.rb`: прогон публичной очереди с зафиксированным в README
  seed даёт хотя бы одну операцию с двумя реальными попытками и `reason: 'next_in_cascade'`
  во второй; та же операция сохраняет `selected_provider` из множества допустимых.
  Спек обязан ссылаться на README комментарием — если кто-то поменяет seed в README,
  спек останется единственным источником правды и разойдётся; поэтому seed берётся
  константой в спеке и упоминается в README тем же числом.

## Что может сломаться молча

| Риск | Чем ловится |
|---|---|
| Демо-команда в README перестала показывать ретрай после смены калибровки/seed | `retry_demo_spec` |
| Ссылка приписана файлу, который делает другое | ручная сверка кодера + требование доложить расхождение |
| Числа 0.0 и 5.0 в README устарели после П1/П4 | П5 идёт после П4; кодер вписывает числа из фактического вывода раннера, а не из этого брифа |

## Если П7 порезан

Тогда переключателя нет, и раздел 1 пишется в короткой редакции: цитата ТЗ, наше
поведение, три опоры (QA дважды и эталонные кейсы), одна фраза «буквальная трактовка
ТЗ рассматривалась, решение отложено осознанно, вопрос выписан организаторам —
`docs/QUESTIONS_FOR_EXPERTS.md`, В-2». Пункты 4-6 раздела 1 при этом опускаются
целиком; выдумывать числа цены нельзя.
