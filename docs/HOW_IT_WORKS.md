# Как это работает

Документ для того, кто впервые открывает репозиторий и хочет понять, что здесь
происходит. Не пересказ ТЗ и не список фич: здесь путь данных от входного файла
до выходного и объяснение, почему каждый кусок устроен именно так.

Проверено по коду на 2026-09-05, после фазы P6. Если код и этот файл разойдутся —
прав код, а документ надо чинить.

---

## 0. Что делает программа за один запуск

```
bin/route reference/data/operations_queue_10.json
```

Читает снапшот провайдеров и очередь заявок. Для каждой заявки решает, какому
платёжному провайдеру её отдать, симулирует ответ провайдера, обновляет
счётчики и переходит к следующей. В конце пишет два файла: решения по каждой
заявке и аналитический отчёт по всей очереди.

Ни базы, ни сети, ни веба. Вход — файлы, выход — файлы. Один прогон занимает
доли секунды.

Главное свойство: **два прогона одного входа дают побайтово одинаковый выход**.
Отсюда растут почти все нетривиальные решения в коде.

## 1. С чего начать читать

Порядок, в котором код разворачивается сам собой. Если пройти его сверху вниз,
дальше можно открывать любой файл — контекст уже будет.

| Шаг | Файл | Что понять |
|---|---|---|
| 1 | `bin/route` | весь пайплайн одним куском: загрузка → цикл по очереди → запись |
| 2 | `lib/domain/provider.rb`, `lib/domain/operation.rb` | что такое провайдер и заявка, какие у них поля |
| 3 | `lib/routing/planner.rb` | как из снапшота получается каскад для одной заявки |
| 4 | `lib/routing/constraints/` | девять проверок допуска, по файлу на проверку |
| 5 | `lib/routing/strategies/count_share.rb` | как устроена стратегия ранжирования |
| 6 | `lib/execution/executor.rb` | как каскад исполняется и что бывает при отказе |
| 7 | `lib/state/providers.rb` | счётчики: резерв, коммит, откат |
| 8 | `lib/reporting/report_builder.rb` | из чего собирается отчёт |

Дальше по желанию: `lib/routing/layers/` (модификаторы порядка),
`lib/offline/` (расчёты для отчёта), `lib/config/` (валидация YAML).

Быстрый способ увидеть систему в работе, не читая ничего:

```bash
bundle exec bin/route reference/data/operations_queue_10.json
```

Печатает по строке на заявку с объяснением выбора, потом сводку.

## 2. Словарь

Пять слов, без которых дальше не читается.

**Провайдер** — платёжный партнёр (`vipay`, `payflow`, `quickpay`). У него
лимиты, список банков, конверсия, целевая доля трафика.

**Операция (заявка)** — одна выплата: сумма, банк, идентификатор.

**Допуск (hard-constraint)** — проверка «можно ли вообще отдать эту заявку
этому провайдеру». Ответ да/нет, компромиссов нет.

**Стратегия (soft-goal)** — правило «кого из допущенных предпочесть». Не
запрещает, а упорядочивает.

**Каскад** — упорядоченный список провайдеров для одной заявки. Первый —
основной выбор, остальные — на случай отказа.

Ключевое разделение всей системы: **сначала допуск отвечает «кому можно», потом
стратегия отвечает «кого первым»**. Стратегия не может вернуть в игру
провайдера, отсечённого допуском, — это инвариант, на него есть отдельный тест.

## 3. Путь одной заявки

Возьмём `op_103`: 150 000 ₽, банк `sberbank`.

### 3.1 Допуск: кто вообще может

`Routing::Planner#plan` берёт всех внешних провайдеров (все, кроме
`spacepayments`) и прогоняет каждого через восемь проверок из
`Constraints::REGISTRY`. Проверки идут по порядку, останавливаются на первом
нарушении — провайдеру достаточно провалить одну.

| Проверка | Причина отсева |
|---|---|
| `Status` — провайдер активен | `provider_inactive` |
| `TrafficShare` — доля трафика не ноль | `zero_traffic_share` |
| `AmountRange` — сумма в пределах лимитов | `amount_below_minimum` / `amount_exceeds_limit` |
| `DailyLimit` — дневной лимит не переполнится | `daily_limit_exceeded` |
| `InProgress` — лимит одновременных заявок | `in_progress_limit_exceeded` |
| `BankFilter` — банк в списке | `bank_not_in_list` |
| `Margin` — маржа не отрицательная | `negative_margin` |
| `Requisites` — есть свободные реквизиты | `no_requisites` |

Для `op_103`: у `vipay` максимум 100 000 — отсев. У `payflow` максимум 50 000 —
отсев. Остаётся `quickpay` с максимумом 200 000.

Отсеянные не выбрасываются: каждый попадает в результат с причиной и числами
(`"150000 > limit_amount_max 100000"`). Правило команды — **причина без числа
не принимается**: жюри оценивает объяснимость, а «не подошёл» ничего не
объясняет.

Названия причин взяты дословно из эталонного файла организаторов
(`lib/routing/reasons.rb`), потому что их валидатор сверяет посимвольно.

**Девятая проверка стоит отдельно.** `RateLimit` (интенсивность) намеренно не
входит в `REGISTRY` и живёт отдельным этапом в `Planner#apply_rate_limit`.
Причина в том, что валидатор организаторов про интенсивность не знает, поэтому
наш отсев по ней может только разойтись с их эталоном. Правило смягчено: фильтр
применяется, **только если после него остаётся хотя бы один кандидат**; если
ограничение опустошает пул — оно не применяется, и этот факт пишется в объяснение
с числами. Держи проверку в общем реестре — смягчение обошло бы `Achievable` и
офлайн-расчёты, и они считали бы допуск строже, чем реальный роутинг. Вопрос о
правильности такой трактовки задан организаторам (`docs/QUESTIONS_FOR_EXPERTS.md`,
В-1).

### 3.2 Стратегия: кто первый

Допущенных упорядочивает стратегия. Контракт жёсткий: она возвращает
**перестановку** входного списка — не добавляет, не удаляет, не заглядывает в
будущие заявки. Нарушение ловится сразу (`validate_permutation!`).

Боевая стратегия — `count_share`, метод делителей Сент-Лагю. Идея: у каждого
провайдера есть целевая доля (40 / 35 / 25), и на каждом шаге заявку получает
тот, кто сильнее отстал от своей доли. Формально сравнивается
`вес / (2 × выдано + 1)`, у кого больше — тот первый.

Сравнение дробей идёт **перекрёстным умножением целых**, без float:

```ruby
left_value  = left_weight  * divisor(right, state)
right_value = right_weight * divisor(left,  state)
```

Это не педантизм. Float сравнивается по-разному на разных платформах, а нам
нужна побайтовая воспроизводимость.

Всего стратегий восемь, каждая — отдельный файл в `lib/routing/strategies/`:

| Имя | Что делает |
|---|---|
| `count_share` | доли по числу заявок (Сент-Лагю) — **боевая** |
| `volume_share` | доли по сумме денег |
| `priority` | обход по полю `priority` |
| `amount_range` | полосы суммы влияют на выбор, а не только фильтруют |
| `conversion` | предпочитает провайдеров с высокой наблюдаемой конверсией |
| `load` | предпочитает наименее загруженных |
| `obligations` | тянет вверх не набравших дневной минимум оборота |
| `round_robin` | наивная ротация — baseline для сравнения, в бою не используется |

Активная выбирается строкой в `config/routing.yml`. Новая стратегия — это файл
в каталоге плюс строка в конфиге: `bin/route` и реестр о ней знать не обязаны
(`Strategies.load_all!` грузит каталог целиком).

### 3.3 Слои и селектор: если целей несколько

Над стратегией есть два необязательных механизма.

**Слои** (`lib/routing/layers/`) двигают уже готовый порядок. `budget_headroom`
— это BALANCE из AdWords: провайдер с исчерпывающимся дневным бюджетом уступает
тем, у кого запас есть. `share_ceiling` не даёт превысить целевую долю. Слой
физически не может вернуть отсечённого допуском — после него порядок снова
проверяется на перестановку.

**Селектор** (`lib/routing/selector.rb`) выбирает саму стратегию по правилам из
конфига: например, крупные суммы — одной стратегией, мелкие — другой. Правила
намеренно не получают очередь целиком, только текущую заявку.

В боевом конфиге `layers: []` — слои выключены. Это не забывчивость: замер
показал, что с ними максимальное отклонение растёт с 5 до 25 п.п. Чтобы решение
не выглядело голословным, в отчёте есть секция `comparison` с числами по трём
конфигурациям (см. §6.3).

### 3.4 Исполнение: попытка, отказ, следующий

`Execution::Executor` идёт по каскаду сверху вниз. Для каждого кандидата:

1. `state.reserve(provider, operation)` — счётчики занимаются **до** ответа;
2. спрашивает исход у источника исходов;
3. реагирует:

| Исход | Что делает | Каскад |
|---|---|---|
| `approved` | `commit` — дневной оборот растёт, `in_progress` освобождается | закончен |
| `rejected` | `rollback` — всё возвращается как было | следующий кандидат |
| `expired` | `hold` — резерв держится, счётчики не трогаются | закончен |

Почему резерв ставится заранее, а не после ответа: пока заявка «в полёте», она
занимает ёмкость провайдера. Не занять её — значит на седьмой заявке
обнаружить, что лимит давно исчерпан, а мы этого не заметили. Незакрытый резерв
тихо ломает допуск, поэтому на инвариант «`in_progress` всегда возвращается к
исходному» есть property-тесты.

`expired` не откатывается сознательно: таймаут — это не отказ, мы просто не
знаем результат. Позже настоящий статус приходит через
`Execution::PendingResolver#resolve`, который вносит дельту по конкретной паре
(заявка, провайдер), не пересчитывая прошлые решения.

### 3.5 Fallback

`spacepayments` — провайдер последней надежды, без лимитов. Он подхватывает
заявку, для которой **ни один внешний провайдер не прошёл допуск** — то есть
fallback по допуску, а не по исходу. Если единственный допустимый провайдер
ответил отказом, в spacepayments заявка по умолчанию не уходит.

ТЗ здесь читается двояко («при отказе исключить и выбрать следующего; если пул
пуст — fallback»), поэтому доступны обе трактовки — ключ `cascade` в конфиге:

```yaml
cascade:
  exhausted: last_candidate    # или fallback_provider — буквальное ТЗ
  on_timeout: stop             # или continue — таймаут продолжает каскад
```

Дефолты воспроизводят прежнее поведение побайтово. Замер показал, что на
публичной очереди все четыре комбинации дают идентичный результат: `op_103` и
`op_104` получают `expired` на единственном допустимом кандидате, где
`continue` эквивалентен `stop`, а исчерпания каскада отказами там не возникает
вовсе. Готовый пример буквальной трактовки — `config/examples/tz_literal.yml`.

## 4. Откуда берутся исходы, если провайдеров нет

Реальных провайдеров не существует, ответ надо симулировать. Наивное решение —
`rand` — убивает воспроизводимость, поэтому используется хеш:

```
roll = SHA256("seed:op_id:provider:attempt_no") % 10000
roll < threshold                → approved
roll < threshold + reject_share → rejected
иначе                           → expired
```

Это чистая функция от четырёх аргументов. Один и тот же вход всегда даёт один и
тот же исход, но распределение выглядит случайным. `attempt_no` в ключе нужен,
чтобы повторная попытка к тому же провайдеру не повторяла его прошлый ответ.

Порог берётся из **наблюдаемой** конверсии, посчитанной по
`operations_history.csv`, а не из паспортной `conversion_24h` в снапшоте. Это
принципиально: у `payflow` заявлено 0.91, а по факту истории — 0.474. Разница
вдвое, и она же попадает в рекомендации отчёта.

Запрет на источники случайности в решающем пути проверяется статически:
`scripts/check_determinism.sh` грепает `lib/routing` и `lib/execution` на
`rand`, `shuffle`, `sample`, `Time.now` и роняет сборку. Поэтому, например,
минутный счётчик интенсивности ключуется полем `created_at` заявки, а не
системными часами.

## 5. Состояние

`State::Providers` — единственное изменяемое место во всей системе. Объекты
провайдеров иммутабельны (`Data.define`), поэтому состояние держит рядом
таблицу изменяемых полей по имени провайдера.

Отслеживается: `in_progress_count` / `in_progress_amount` (сколько в полёте),
`daily_approved_amount` (оборот за день), `available_requisites`, счётчик
запросов в минуту и доли текущего прогона (`ShareLedger`).

Полная таблица переходов:

| Событие | `in_progress` | `daily_approved` | доля |
|---|---|---|---|
| `reserve` | +1, +сумма | — | +1 |
| `commit` (approved) | −1, −сумма | **+сумма** | остаётся |
| `rollback` (rejected) | −1, −сумма | — | **−1** |
| `hold` (expired) | держится | — | остаётся |
| `resolve_hold(:approved)` | −1, −сумма | **+сумма** | остаётся |
| `resolve_hold(:rejected)` | −1, −сумма | — | **−1** |

Единственное сознательное отступление — счётчик интенсивности: он растёт в
`reserve` и **не уменьшается** ни при откате, ни при таймауте. Интенсивность
меряет отправленные запросы, а не занятую ёмкость, поэтому отказ не возвращает
лимит.

## 6. Что на выходе

### 6.1 `routing_decisions_test.json`

Массив решений, по объекту на заявку:

```json
{
  "operation_id": "op_103",
  "selected_provider": "quickpay",
  "attempts": [
    {"provider": "vipay",   "decision": "skipped",
     "reason": "amount_exceeds_limit", "details": "150000 > limit_amount_max 100000"},
    {"provider": "payflow", "decision": "skipped",
     "reason": "amount_exceeds_limit", "details": "150000 > limit_amount_max 50000"},
    {"provider": "quickpay","decision": "selected", "reason": "only_eligible_provider"}
  ],
  "simulated_result": "approved",
  "latency_sec": 28
}
```

В `attempts` попадают **все рассмотренные** провайдеры, а не только выбранный, и
порядок элементов равен порядку рассмотрения.

Одна странность, которая объясняется схемой организаторов: у провайдера,
который отказал, стоит `decision: "selected"`. Валидатор принимает в этом поле
только `selected` и `skipped`, третьего значения нет, поэтому неудачная попытка
кодируется как `selected` плюс `result: "rejected"`. Это ограничение формата, а
не наша семантика.

### 6.2 `routing_report_test.json`

| Секция | Что показывает |
|---|---|
| `distribution` | сколько заявок ушло каждому, факт против цели против достижимого |
| `volume_distribution` | то же по деньгам |
| `attempt_distribution` | реальные попытки и наблюдаемая конверсия |
| `skip_reasons` | сколько раз сработала каждая проверка допуска |
| `projected_daily_utilization` | насколько выбран дневной лимит |
| `fallback` | успех с первой попытки, спасённые каскадом, уходы в spacepayments |
| `benchmark` | сравнение с офлайн-эталоном, `competitive_ratio` |
| `deviation_causes` | числовая причина каждого отклонения больше 5 п.п. |
| `recommendations` | конкретный параметр и значение, а не наблюдение |
| `comparison` | наш аллокатор против наивной ротации и против варианта со слоями |

Про три колонки в `distribution`. Целевое распределение 40/35/25 на этой
очереди **физически недостижимо**: три заявки может взять только `quickpay`
(остальным не позволяют сумма и банк), а у `payflow` кончается дневной лимит.
Поэтому считается ещё и достижимая доля (`Routing::Achievable`), а отклонение
меряется от неё. Это прямой ответ на критерий «поведение системы, если цель
выполнить невозможно»: мы не прячем недостижимость, а показываем её числом.

Внимание на ловушку при чтении отчёта: `benchmark.max_deviation_pp` меряется
**от паспортной цели**, а `distribution.deviation_pp` — **от достижимой**. На
публичной очереди это 5.0 против 0.0. Так сделано потому, что от достижимой
доли бенчмарк вырождается в 0/0 и перестаёт отличать хороший прогон от плохого.
Расхождение объяснено прямо в поле `note` того же блока.

### 6.3 Что считается постфактум

В `lib/offline/` живут расчёты, которые **не участвуют в принятии решений** и
идут только в отчёт. На это есть отдельный тест изоляции
(`spec/offline/isolation_spec.rb`), а не устная договорённость.

**Офлайн-эталон** (`oracle.rb`) — жадный поиск с локальными улучшениями по всей
очереди задним числом. Он честно назван `offline_bound`, а не `optimum`: задача
не разваливается на независимые назначения (одобрение съедает лимит и меняет
допуск для следующих заявок), поэтому гарантии оптимума нет. И оптимален он
относительно **нашего** симулятора исходов, а не относительно того, как исходы
будет генерировать проверяющий.

**Сравнение конфигураций** (`comparison.rb`) — тот же онлайн-проход по той же
очереди под другой стратегией, каждый вариант на своём состоянии. На публичной
очереди: наивная ротация даёт 40 п.п. отклонения от достижимого, наш аллокатор
— 0, он же со слоями — 20. Отсюда видно, что пустой `layers` в боевом конфиге
выбран замером.

## 7. Конфигурация

Всё поведение задаётся `config/routing.yml`, без правки кода: активная
стратегия, слои и их пороги, правила селектора, полосы сумм, источник исходов и
seed, режим каскада, список вариантов сравнения, fallback-провайдер.

Конфиг проходит валидацию схемы при загрузке (`lib/config/`): неизвестная
стратегия, несуществующий слой или дубль имени роняют запуск с внятным
сообщением, а не тихо игнорируются.

Приоритет источников: **флаг CLI > YAML > дефолт**. Кода-дефолта стратегии нет
намеренно — имя всегда приходит либо из флага, либо из конфига.

**Два снапшота провайдеров, и это важно.**
`reference/data/providers.json` — файл организаторов, неприкосновенный: по нему
их валидатор считает допуск. `data/providers.json` — наш, он же используется по
умолчанию. Отличается ровно четырьмя полями, которые ТЗ разрешает добавить
самим (`volume_share_pct`, `requests_per_minute_limit`, `daily_turnover_min`,
`daily_turnover_max`). На это отличие есть тест: разница ключей между файлами
обязана быть ровно этим набором. Смысл конструкции в том, что зелёный
`make validate` продолжает доказывать нужное свойство — наши решения допустимы
**по снапшоту организаторов**, а не по нашему собственному.

## 8. Как проверяется

```bash
make gate       # rspec + rubocop + статическая проверка на источники случайности
make validate   # валидатор организаторов на публичной очереди
make determinism # два прогона подряд, diff обязан быть пустым
make deliver    # боевые файлы в корень репозитория
```

Гейт и валидатор — **разные вещи**. Гейт говорит «наш код не сломан», валидатор
— «наш вывод примут». Зелёными должны быть оба, и вердикт валидатора важнее
нашего мнения о правильности.

Что проверяет валидатор организаторов: покрытие всех заявок, структуру JSON,
четыре детерминированных кейса (где допустимый провайдер единственный) и что
выбранный провайдер входит в множество допустимых по их снапшоту.

Текущее состояние: 664 примера rspec, 0 нарушений rubocop, валидатор 29/0/0.

## 9. Инварианты

То, что нельзя нарушать. Код, который их нарушает, неверен независимо от того,
насколько он элегантен.

1. **Детерминизм.** Два прогона одного входа — побайтово одинаковый выход.
   В `lib/routing` и `lib/execution` запрещены `rand`, `shuffle`, `sample`,
   `Time.now`. Проверяется статически.
2. **Целые числа в решающем пути.** Дроби сравниваются перекрёстным
   умножением, веса — в базисных пунктах.
3. **Причины отсева — дословно** из эталона организаторов. Своих формулировок
   не изобретаем.
4. **`decision` только `selected` или `skipped`.** Любое третье значение
   валидатор считает ошибкой структуры.
5. **Выбранный провайдер обязан быть допустим по исходному снапшоту.** Наши
   списания лимитов пул только сужают, поэтому безопасны; добавленные нами поля
   тоже вправе лишь сужать.
6. **Онлайн-обработка.** Заглядывать в будущие заявки очереди нельзя —
   организаторы подтвердили, что каждая операция получает свой снимок.
   Исключение — расчёты в `lib/offline/`, они идут только в отчёт.
7. **Резерв, а не пост-фактум.** Счётчики занимаются в момент попадания в
   каскад, а не после ответа.
8. **Причина без числа не принимается.** Каждое объяснение содержит конкретное
   сравнение.

## 10. Чего здесь сознательно нет

| Нет | Почему |
|---|---|
| Нейросетей и ML | прямой запрет ТЗ, дисквалификация |
| Rails, БД, очередей | вход — файлы, выход — файлы; баллов не даёт |
| Единого «smart score» из десяти слагаемых | необъяснимо, а объяснимость оценивается отдельно |
| HTML-дашборда | организаторы ответили, что визуализация по желанию; порезано осознанно |
| Оптимизации по марже сверх проверки допуска | в критериях отсутствует |
