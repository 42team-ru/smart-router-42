## 1. Гейт и валидатор (~40 сек)

```bash
make gate
make validate
make determinism
```

Три факта одной командой каждый: код не сломан, вывод примут, два прогона
побайтово совпадают. Не спорим о детерминизме — показываем `diff -q`.

## 2. Живой прогон — теперь виден без `cat` (~1 мин)

```bash
bundle exec bin/route reference/data/operations_queue_10.json --out-dir /tmp/demo
```

Раньше здесь был `cat routing_decisions_test.json` и разбор глазами — теперь
то же самое печатает сам `bin/route` (D-1, `Reporting::ConsoleSummary`):
по строке на операцию (провайдер, исход, причина с числом) и сводка внизу
(распределение факт/цель/достижимо, fallback, benchmark, причины отклонений,
рекомендации).

Что показать пальцем в выводе:
- `op_103  150 000 ₽ → quickpay (expired)  only_eligible_provider: ...,
  других допустимых нет` — решение предопределено данными, и видно почему;
- `op_107  800 ₽ → payflow (approved)  only_eligible_provider: ...` —
  тот самый провайдер, вокруг которого построена ловушка бюджета (см. §3);
- в сводке — `Причина отклонения: quickpay +5 п.п. к цели: op_103, op_104,
  op_108 не имели альтернатив по сумме и банку` и `Рекомендация: retarget:
  ... максимальное отклонение падает с 5 до 0 п.п.` — на чекпоинте это были
  пустые поля в структуре, теперь реальные вычисленные строки (Ф5).

## 3. Слои поверх стратегии — ψ бережёт headroom (~1.5 мин)

```bash
bundle exec bin/route reference/data/operations_queue_10.json \
  --config config/examples/adwords.yml --out-dir /tmp/demo_adwords
```

Что видно построчно: с `budget_headroom` payflow подвинут для op_101/102/110
(psi упал ниже порога 0.100 — видно прямо в строке `budget_headroom: payflow
psi 0.033 (отклонение 67216) -> с 1 на 2`), но **op_107 остаётся за payflow**
(единственный допустимый). Ровно то, что доказывает
`spec/bin/adwords_config_spec.rb`.

**Честно, если спросят:** `competitive_ratio` в этом прогоне вырастет (было
1.0 на дефолтном конфиге, здесь заметно выше) — не потому что ψ работает
хуже, а потому что `benchmark` меряет отклонение от **паспортной** цели
(40/35/25), а ψ сознательно оптимизирует другое — сохранение бюджетного
запаса payflow, а не попадание в паспортную долю. Два разных критерия дают
разные числа на одних данных, и это не противоречие, а ровно то, что описано
в `ARCHITECTURE.md` §12 про `distribution.deviation_pp` (от достижимого) и
`benchmark.max_deviation_pp` (от паспортного) — здесь та же логика,
только для сравнения "без слоя / со слоем", а не "достижимое / паспортное".

## 4. Selector — правило вместо флага (~1 мин)

```bash
bundle exec bin/route reference/data/operations_queue_10.json \
  --config config/examples/selector.yml --out-dir /tmp/demo_selector
```

В выводе видно сработавшее правило по каждой операции:
```
op_102  ...  selector: правило #1 (amount 48000 >= 40000) -> load (причина: крупная операция направляется к менее загруженному провайдеру)
op_104  ...  selector: правило #2 (eligible_count 1 <= 1) -> priority (причина: выбора нет, каскад тривиален)
op_101  ...  selector: 0 правил из 2 совпало, amount 15000 < 40000 -> default count_share
```
Стратегия переключается конфигом на лету, по операции — не флагом на весь
прогон.

| Мин | Что |

| 5:00 | Selector: правило вместо флага (§4) |
| 6:00 | Target/Achievable/Actual + Ф5 вживую: deviation_causes, retarget (§3.3 CHECKPOINT_TALK) |

**Три прогона подряд:** прогнать весь список выше три раза без остановки,
засечь суммарное время каждый раз, сверить, что распределения (`split` по
`selected_provider`) совпадают между прогонами байт в байт — на пункте 2
(дефолтный конфиг) это гарантирует `make determinism`, здесь проверяется на
полном сценарии, включая слои и Selector.
