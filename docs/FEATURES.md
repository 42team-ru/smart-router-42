# Реализованные фичи — smart-router-42

## Что за проект

Движок умного роутинга платёжных выплат. Получает на вход снапшот провайдеров и очередь заявок, прогоняет каждую заявку через фильтры и стратегию, выбирает лучшего провайдера и записывает два JSON-файла: решения по каждой заявке и аналитический отчёт.

Никакой БД, никакого веба, никакого ML — офлайн, чистый Ruby.

---

## Входные данные

| Файл | Что внутри |
|------|-----------|
| `reference/data/providers.json` | Снапшот 4 провайдеров: vipay (40%), payflow (35%), quickpay (25%), spacepayments (fallback). 27 полей на каждого: лимиты, банки, маржа, конверсия, реквизиты |
| `reference/data/operations_queue_10.json` | 10 операций: сумма, банк, карта, реквизиты |
| `operations_history.csv` | История предыдущих транзакций — используется для калибровки конверсии |

Загрузка в `lib/io/`: три отдельных загрузчика, каждый валидирует данные и сообщает об ошибках не падая.

## 9 жёстких фильтров (hard constraints)

Каждый фильтр — отдельный класс в `lib/routing/constraints/`. Проверяются по очереди, стоп на первом нарушении. Если провайдер не прошёл — он попадает в `attempts` как `skipped` с причиной и деталями (всегда с числами).

| # | Фильтр | Что проверяет | Причина отсева |
|---|--------|--------------|----------------|
| R-1 | Status | статус провайдера == "active" | `provider_inactive` |
| R-2 | TrafficShare | traffic_percentage > 0 | `zero_traffic_share` |
| R-3 | AmountRange | сумма операции в пределах [min, max] | `amount_below_minimum` / `amount_exceeds_limit` |
| R-4 | DailyLimit | дневное одобренное + сумма ≤ дневной лимит | `daily_limit_exceeded` |
| R-5 | InProgress | операций/суммы в процессе + новая ≤ лимит | `in_progress_limit_exceeded` |
| R-6 | BankFilter | банк есть в whitelist или нет в blacklist | `bank_not_in_list` |
| R-7 | Margin | маржа провайдера ≤ маржа мерчанта | `negative_margin` |
| R-8 | Requisites | доступных реквизитов > 0 | `no_requisites` |
| R-9 | RateLimit | запросов за минуту + 1 ≤ лимит | `rate_limit_exceeded` |

Формулировки причин дословно совпадают с эталоном организаторов — валидатор это проверяет.

Детали всегда содержат конкретные числа: `"150000 > limit_amount_max 100000"`, `"bank alfa не входит в banks [sberbank, tinkoff] (2 банков)"`.

## Стратегии ранжирования

После фильтрации оставшиеся провайдеры ранжируются стратегией. Реализованы две:

### CountShare (Saint-Laguë)
Ранжирует так, чтобы итоговое распределение транзакций сошлось к целевым долям (vipay 40%, payflow 35%, quickpay 25%).

Формула: провайдер с наибольшим `вес / (2 × выданных + 1)` идёт первым. Кто "недобирает" от своей квоты — получает приоритет. Сравнение через перекрёстное умножение, без float.

### VolumeShare
То же самое, но по сумме денег, а не по количеству транзакций. Считает дефицит: `(целевой_вес × общий_объём) - (10000 × объём_провайдера)`. Кто больше отстаёт по деньгам — тот первый.

Стратегии регистрируются в реестре и выбираются по имени (`count_share`, `volume_share`). Добавить новую — один файл.

## State machine — учёт состояния провайдеров

`lib/state/providers.rb` — центральный объект, хранит состояние всех провайдеров в памяти.

На каждого провайдера отслеживается:
- `in_progress_count` / `in_progress_amount` — сколько операций сейчас в полёте
- `daily_approved_amount` — сколько одобрено за день
- `available_requisites` — остаток реквизитов

Пять переходов состояния:

| Событие | Когда | in_progress | daily_approved | доля в шере |
|---------|-------|-------------|----------------|-------------|
| `reserve` | перед попыткой | +1, +amount | не меняется | +units |
| `commit` | исход approved | -1, -amount | **+amount** | остаётся |
| `rollback` | исход rejected | -1, -amount | не меняется | **-units** |
| `hold` | исход expired | остаётся | не меняется | остаётся |
| `resolve_hold` :approved | поздний статус | -1, -amount | **+amount** | остаётся |
| `resolve_hold` :rejected | поздний статус | -1, -amount | не меняется | **-units** |

Инвариант: после завершения операции `in_progress` всегда возвращается к исходному значению.

## Executor — каскад попыток

`lib/execution/executor.rb` прогоняет операцию через план:

```
Для каждого кандидата по порядку:
  1. reserve(provider, operation)
  2. спросить outcome source → :approved / :rejected / :expired
  3. approved  → commit → стоп, операция завершена
     rejected  → rollback → переходим к следующему
     expired   → hold → стоп, операция зависла (PendingResolver разберётся)

Если кандидатов не было вообще → fallback на spacepayments
```

Spacepayments — fallback по допуску (ни один внешний провайдер не прошёл фильтры), а не по исходу (если провайдер ответил rejected — это не повод переключиться на spacepayments).

### PendingResolver

Когда операция получила `:expired` — она зависает в hold. Когда приходит настоящий статус, `PendingResolver#resolve(actual: :approved/:rejected)` применяет дельту: освобождает hold и корректирует state. Другие операции не пересчитываются.

## Outcome sources — симуляция ответа провайдера

Чтобы не ходить в реальные API, исход симулируется. Реализовано четыре источника:

| Класс | Поведение | Когда нужен |
|-------|-----------|-------------|
| `Deterministic` | SHA256(seed + op_id + provider + attempt_no) → воспроизводимый исход | основной режим |
| `Scripted` | YAML-файл с явными исходами для каждой пары (op, provider) | тесты конкретных сценариев |
| `AlwaysOk` | всегда `:approved` | тест каскада |
| `AlwaysFail` | всегда `:rejected` | тест исчерпания каскада |

`Deterministic` работает так: вычисляет хеш, берёт остаток от деления на 10000 и сравнивает с порогом конверсии провайдера. Конверсия берётся из истории (`history.csv`), а не из снапшота. Никакого `rand` — два прогона дают побайтово одинаковый результат.

## Два выходных файла

### routing_decisions_test.json

Для каждой операции:
- `selected_provider` — кто выбран
- `attempts` — все попытки в порядке каскада (и selected, и skipped), с reason, details, strategy, attempt_no
- `simulated_result` — итоговый исход
- `latency_sec` — задержка выбранного провайдера

### routing_report_test.json

Аналитика по всей очереди:

| Раздел | Что показывает |
|--------|---------------|
| `distribution` | сколько операций досталось каждому провайдеру, доля% vs цель% |
| `volume_distribution` | то же, но по суммам |
| `attempt_distribution` | реальные попытки, наблюдаемая конверсия |
| `skip_reasons` | сколько раз сработал каждый фильтр |
| `projected_daily_utilization` | использование дневного лимита в % |
| `fallback` | first_attempt_success, recovered_by_fallback, spacepayments_used |
| `recommendations` | советы: где конверсия расходится с заявленной, где заканчивается лимит |
| `benchmark` | заглушка (заполняется в Ф5) |

## Тесты и проверки

```
make gate     → 341 тест, 0 ошибок | rubocop: 0 нарушений | детерминизм: ок
make validate → 29 проверок ✅, 0 ошибок ❌
```

Что проверяет валидатор организаторов:
1. Все 10 операций есть в файле
2. Структура JSON: обязательные поля, `decision` только `selected`/`skipped`
3. 4 детерминированных кейса (единственный возможный провайдер)
4. `selected_provider` входит в список допустимых по фильтрам
5. Для 13 ожидаемых пар (операция → провайдер) есть `skipped` attempt

Дополнительно `make gate` проверяет статически что в `lib/routing` и `lib/execution` нет `rand`, `shuffle`, `sample`, `Time.now`, и запускает два прогона для проверки побайтовой идентичности вывода.
