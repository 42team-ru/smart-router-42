# Реализованные фичи — smart-router-42

## Что за проект

Движок умного роутинга платёжных выплат. Получает на вход снапшот провайдеров и очередь заявок, прогоняет каждую заявку через фильтры и стратегию, выбирает лучшего провайдера и записывает два JSON-файла: решения по каждой заявке и аналитический отчёт.

Никакой БД, никакого веба, никакого ML — офлайн, чистый Ruby.

---

## Входные данные

| Файл | Что внутри |
|------|-----------|
| `reference/data/providers.json` | Снапшот 4 провайдеров: vipay (40%), payflow (35%), quickpay (25%), spacepayments (fallback). 27 полей на каждого: лимиты, банки, маржа, конверсия, реквизиты |
| `reference/data/operations_queue_10.json` | 10 операций: сумма, банк, карта, реквизиты |
| `operations_history.csv` | История предыдущих транзакций — используется для калибровки конверсии |

Загрузка в `lib/io/`: три отдельных загрузчика, каждый валидирует данные и сообщает об ошибках не падая.

## 8 жёстких фильтров (hard constraints) + отдельный этап интенсивности

Каждый фильтр — отдельный класс в `lib/routing/constraints/`. Проверяются по очереди, стоп на первом нарушении. Если провайдер не прошёл — он попадает в `attempts` как `skipped` с причиной и деталями (всегда с числами).

| # | Фильтр | Что проверяет | Причина отсева |
|---|--------|--------------|----------------|
| R-1 | Status | статус провайдера == "active" | `provider_inactive` |
| R-2 | TrafficShare | traffic_percentage > 0 | `zero_traffic_share` |
| R-3 | AmountRange | сумма операции в пределах [min, max] | `amount_below_minimum` / `amount_exceeds_limit` |
| R-4 | DailyLimit | дневное одобренное + сумма ≤ дневной лимит | `daily_limit_exceeded` |
| R-5 | InProgress | операций/суммы в процессе + новая ≤ лимит | `in_progress_limit_exceeded` |
| R-6 | BankFilter | банк есть в whitelist или нет в blacklist | `bank_not_in_list` |
| R-7 | Margin | маржа провайдера ≤ маржа мерчанта | `negative_margin` |
| R-8 | Requisites | доступных реквизитов > 0 | `no_requisites` |

`Constraints::REGISTRY` (`lib/routing/constraints.rb`) несёт ровно эти восемь — валидатор
организаторов про интенсивность не знает и в допуск её не закладывает (`docs/QUESTIONS_FOR_EXPERTS.md`,
В-1), поэтому строгий девятый фильтр разошёлся бы с эталоном молча. Интенсивность
(`requests_per_minute_limit`) считается отдельным этапом планирования
(`Routing::Planner#apply_rate_limit`), после сборки каскада: отсеивает кандидата, только
если после отсева в пуле остаётся хотя бы один внешний — иначе ограничение не
применяется и это пишется в `details` с числами. Наше смягчение до ответа экспертов, вопрос
задан (`docs/QUESTIONS_FOR_EXPERTS.md`, В-1).

Формулировки причин дословно совпадают с эталоном организаторов — валидатор это проверяет.

Детали всегда содержат конкретные числа: `"150000 > limit_amount_max 100000"`, `"bank alfa не входит в banks [sberbank, tinkoff] (2 банков)"`.

## Стратегии ранжирования, слои и селектор

После фильтрации оставшиеся провайдеры ранжируются стратегией. `Routing::Strategies.known`
после `load_all!` несёт **восемь** зарегистрированных имён (было две на момент Ф2, остальные
шесть — Ф3/П3):

| Стратегия | Идея |
|---|---|
| `count_share` | дивизорный аллокатор долей (Сент-Лагю), см. ниже |
| `volume_share` | то же, но по деньгам (дефицитный аллокатор, см. ниже) |
| `priority` | порядок по полю `priority` снапшота |
| `amount_range` | полосы суммы из конфига (`amount_ranges`) предпочитают конкретного провайдера |
| `conversion` | порядок по заявленной `conversion_24h` |
| `load` | порядок по свободной ёмкости (`in_progress`/лимиты) |
| `obligations` | порядок по дневным оборотным обязательствам (`daily_turnover_min/max`, П1) |
| `round_robin` | детерминированная круговая ротация без учёта веса; не боевой кандидат — baseline для офлайн-сравнения (см. ниже, П3/П4) |

### CountShare (метод Сент-Лагю)
Ранжирует так, чтобы итоговое распределение транзакций сошлось к целевым долям (vipay 40%, payflow 35%, quickpay 25%).

Формула: провайдер с наибольшим `вес / (2 × выданных + 1)` идёт первым — классический
дивизорный ряд Сент-Лагю (1, 3, 5, …). Кто "недобирает" от своей квоты — получает приоритет.
Сравнение через перекрёстное умножение, без float.

### VolumeShare (Deficit Round Robin)
То же самое, но по сумме денег, а не по количеству транзакций. Считает дефицит: `(целевой_вес × общий_объём) - (10000 × объём_провайдера)`. Кто больше отстаёт по деньгам — тот первый. Это дефицитный аллокатор в духе Deficit Round Robin (Shreedhar, Varghese, 1996); `round_robin` — его вырожденный случай при равных весах.

Стратегии регистрируются в реестре и выбираются по имени. Добавить новую — один файл
плюс строка `strategy:` в конфиге (README §7).

### Слои (Ф4) и селектор

Поверх ранжирования стратегии можно добавить **слои** — лексикографические мягкие
модификаторы (`lib/routing/layers/`, реестр `Routing::Layers`, сейчас два: `budget_headroom`
— BALANCE/AdWords (Mehta et al., FOCS 2005), `share_ceiling` — потолок доли). Слой не
расширяет множество допущенных, только переставляет уже допущенных по кортежу отклонений
(`Routing::LayerStack`, преемптивное/лексикографическое goal programming: первый слой в
списке старше). Боевой конфиг держит `layers: []` — включение измеримо ухудшает
распределение на публичной очереди (README §4 «Сравнение стратегий», числа из
`Offline::Comparison`, П4).

`strategy_selection` (Ф4/X-3) позволяет выбирать стратегию по правилам текущей операции
(`amount_gte`, `amount_lt`, `bank_in`, `eligible_count_lte`) вместо одной статической —
пример `config/examples/selector.yml`.

## State machine — учёт состояния провайдеров

`lib/state/providers.rb` — центральный объект, хранит состояние всех провайдеров в памяти.

На каждого провайдера отслеживается:
- `in_progress_count` / `in_progress_amount` — сколько операций сейчас в полёте
- `daily_approved_amount` — сколько одобрено за день
- `available_requisites` — остаток реквизитов

Пять переходов состояния:

| Событие | Когда | in_progress | daily_approved | доля в шере |
|---------|-------|-------------|----------------|-------------|
| `reserve` | перед попыткой | +1, +amount | не меняется | +units |
| `commit` | исход approved | -1, -amount | **+amount** | остаётся |
| `rollback` | исход rejected | -1, -amount | не меняется | **-units** |
| `hold` | исход expired | остаётся | не меняется | остаётся |
| `resolve_hold` :approved | поздний статус | -1, -amount | **+amount** | остаётся |
| `resolve_hold` :rejected | поздний статус | -1, -amount | не меняется | **-units** |

Инвариант: после завершения операции `in_progress` всегда возвращается к исходному значению.

## Executor — каскад попыток

`lib/execution/executor.rb` прогоняет операцию через план:

```
Для каждого кандидата по порядку:
  1. reserve(provider, operation)
  2. спросить outcome source → :approved / :rejected / :expired
  3. approved  → commit → стоп, операция завершена
     rejected  → rollback → переходим к следующему
     expired   → hold → стоп, операция зависла (PendingResolver разберётся)

Если кандидатов не было вообще → fallback на spacepayments
```

Spacepayments — fallback по допуску (ни один внешний провайдер не прошёл фильтры), а не по исходу (если провайдер ответил rejected — это не повод переключиться на spacepayments).

### PendingResolver

Когда операция получила `:expired` — она зависает в hold. Когда приходит настоящий статус, `PendingResolver#resolve(actual: :approved/:rejected)` применяет дельту: освобождает hold и корректирует state. Другие операции не пересчитываются.

## Outcome sources — симуляция ответа провайдера

Чтобы не ходить в реальные API, исход симулируется. Реализовано четыре источника:

| Класс | Поведение | Когда нужен |
|-------|-----------|-------------|
| `Deterministic` | SHA256(seed + op_id + provider + attempt_no) → воспроизводимый исход | основной режим |
| `Scripted` | YAML-файл с явными исходами для каждой пары (op, provider) | тесты конкретных сценариев |
| `AlwaysOk` | всегда `:approved` | тест каскада |
| `AlwaysFail` | всегда `:rejected` | тест исчерпания каскада |

`Deterministic` работает так: вычисляет хеш, берёт остаток от деления на 10000 и сравнивает с порогом конверсии провайдера. Конверсия берётся из истории (`history.csv`), а не из снапшота. Никакого `rand` — два прогона дают побайтово одинаковый результат.

## Два выходных файла

### routing_decisions_test.json

Для каждой операции:
- `selected_provider` — кто выбран
- `attempts` — все попытки в порядке каскада (и selected, и skipped), с reason, details, strategy, attempt_no
- `simulated_result` — итоговый исход
- `latency_sec` — задержка выбранного провайдера

### routing_report_test.json

Аналитика по всей очереди:

| Раздел | Что показывает |
|--------|---------------|
| `distribution` | сколько операций досталось каждому провайдеру, доля% vs цель% vs **достижимая%** (`Routing::Achievable`) и `deviation_pp` от достижимой |
| `volume_distribution` | то же, но по суммам |
| `attempt_distribution` | реальные попытки, наблюдаемая конверсия |
| `skip_reasons` | сколько раз сработал каждый фильтр |
| `projected_daily_utilization` | использование дневного лимита в % |
| `fallback` | first_attempt_success, recovered_by_fallback, spacepayments_used, cascade_exhausted |
| `deviation_causes` | структурная причина каждого отклонения от цели (единственный допустимый провайдер, дневной лимит, «причина не определена») — считает `Reporting::DeviationCauses`, реальные числа, не заглушка |
| `recommendations` | советы: где конверсия расходится с заявленной, где заканчивается лимит, плюс `retarget:` — предложенные достижимые цели вместо паспортных, когда недостижимость объяснена структурно (`Reporting::Retarget`, X-6) |
| `benchmark` | офлайн-эталон (`Offline::Oracle`: жадный старт + локальные улучшения, ограничено 500 операциями) против нашего онлайн-результата, `competitive_ratio`; считается по-настоящему (X-4/X-5), не заглушка — заглушка остаётся только дефолтом `Reporting::ReportBuilder.build` без kwarg-а `benchmark`, чего боевой `bin/route` не делает никогда |
| `comparison` | офлайн-сравнение конфигураций (`strategy`+`layers`) на той же очереди — ключ `comparison` в конфиге, П4; отсутствует в отчёте, если ключ пуст |

## Тесты и проверки

```
make gate     → 664 теста, 0 падений | rubocop: 169 файлов, 0 нарушений | детерминизм: источников случайности нет
make validate → Пройдено: 29, Ошибок: 0, Предупр.: 0
```

Числа сняты фактическим прогоном (см. отчёт по пакету П6); растут с каждым пакетом —
если после этого пакета что-то ещё доделывается, числа обновляются в том же пакете, где
меняется код (`docs/plans/P6/README.md`, риск-таблица П6).

Что проверяет валидатор организаторов:
1. Все 10 операций есть в файле
2. Структура JSON: обязательные поля, `decision` только `selected`/`skipped`
3. 4 детерминированных кейса (единственный возможный провайдер)
4. `selected_provider` входит в список допустимых по фильтрам
5. Для 13 ожидаемых пар (операция → провайдер) есть `skipped` attempt

Дополнительно `make gate` проверяет статически что в `lib/routing` и `lib/execution` нет `rand`, `shuffle`, `sample`, `Time.now`, и запускает два прогона для проверки побайтовой идентичности вывода.

## Что сделано в Ф3–Ф6

Этот раздел раньше назывался «Что ещё не реализовано» и перечислял уже написанный код как
несделанный — дороже всего это стоит в критерии «полнота проработки решения». Ниже —
фактическое состояние, снятое прогоном, а не памятью документа.

- **5 дополнительных стратегий ранжирования** (Priority, AmountRange, Conversion, Load,
  Obligations) плюс **шестая**, `round_robin` (П3) — baseline для офлайн-сравнения, не
  боевой кандидат. Реестр стратегий: 8 имён (`Routing::Strategies.known`).
- **Управление поведением через `config/routing.yml`** (CFG-1/2/3): стратегия, слои,
  пороги целей, правила выбора стратегии на операцию (`strategy_selection`), источник
  исходов и seed, полосы суммы, обязательства по обороту, ограничение интенсивности,
  переключатель каскада (`cascade`, П7), офлайн-сравнение (`comparison`, П4) — всё
  валидируется схемой (`Config::Loader`), а не читается наугад.
- **Мягкие слои** (soft layers, Ф4): `budget_headroom` (BALANCE/AdWords) и `share_ceiling`
  (потолок доли), лексикографическая композиция (`Routing::LayerStack`, preemptive goal
  programming). Боевой конфиг держит `layers: []` — измеренное решение, не забытая
  функциональность (README §4 «Сравнение стратегий»).
- **Офлайн-оптимум и competitive ratio** (X-4/X-5, `Offline::Oracle`/`Offline::BenchmarkBlock`):
  реальный эвристический эталон (жадный старт + локальные улучшения), считается один раз
  на прогон и передаётся в отчёт готовым хешем — не заглушка.
- **Офлайн-сравнение конфигураций** (П4, `Offline::Comparison`): `round_robin` против боевой
  `count_share` против `count_share` со слоями, на той же очереди, числа — в README §4 и
  в секции `comparison` отчёта.
- **Настраиваемый fallback каскада** (П7): обе трактовки ТЗ (буквальная и наша) доступны
  переключателем `cascade`, дефолт не меняя (README §8).
- **Наш расширенный снапшот провайдеров** (П1/П2): `data/providers.json` — побайтовая копия
  снапшота организаторов плюс `volume_share_pct`/`daily_turnover_min`/`daily_turnover_max`/
  `requests_per_minute_limit`; пристинный `reference/data/providers.json` не тронут
  (`spec/io/providers_snapshot_parity_spec.rb`).

**Не реализовано и не планировалось в этом плане:** circuit breaker (X-7, `docs/TASKS.md`,
`docs/RESEARCH.md` идея 7) — низкий приоритет, «только если останется время»; в план P6
никогда не входил и не режется им.
