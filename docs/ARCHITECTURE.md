Границы работ — в `SCOPE.md`. Роли и график — в `OWNERSHIP.md`.

## 1. Что зафиксировали ответы Q&A

Восемь ответов, каждый из которых что-то отменяет или подтверждает. Это фундамент, ниже
всё построено на них.

| Вопрос | Ответ экспертов | Следствие для нас |
|---|---|---|
| Нужна ли БД, Redis, сторонние сервисы? | «Кейс не требует. Критерии это никак не вознаграждают» | **Чистый Ruby, файлы на вход и выход.** Rails/Postgres/Sidekiq выброшены |
| Нужен ли интерфейс? | «Достаточно скрипта. Интерфейс и скрипт будут одинаково ценены. Главное — понятность» | **Дашборд не строим.** Освободившееся время — в стратегии и аналитику |
| Можно ли ML: random forest, отжиг, регрессия? | «Нейросети нельзя. ML — по минимуму. Хотелось бы алгоритмический вид» | Только детерминированные правила |
| Порог доли Ruby-кода? | «Процента нет, но логика должна быть на Ruby и не фиктивной» | Вся логика в `lib/`, ноль обёрток над чужим кодом |
| Известна ли очередь заранее, можно ли look-ahead? | «Каждая операция получает свой снимок. Не бывает так, что известны наперёд тысяча операций» | **Онлайн-обработка.** Глобальная оптимизация по всей очереди отменена |
| Что если единственный допустимый провайдер исчерпал лимит? | «Предсказать при последовательном проходе почти невозможно. Жёстко штрафоваться не будет» | Ловушку payflow/op_107 не лечим look-ahead'ом, а честно показываем в отчёте |
| Когда фиксируется выбор провайдера? | «Закрепляем в счётчик сразу при попадании в каскад. При отказе — освобождаем по всем коэффициентам, туда может попасть другая операция» | **Резерв → коммит/откат.** Ключевой механизм, §4 |
| Что делать с таймаутом? | «Считаем, что всё хорошо. Если статус-чек вернёт reject — освобождаем коэффициенты. Компенсирующая корректировка с текущего момента» | `expired` не запускает fallback, резерв держится, §7 |
| Кто считает лимиты и обороты? | «Если роутер будет реалтайм счётчики накапливать — это плюс» | Своё состояние в памяти, не пересчёт из истории |
| Что если hard-фильтр не прошёл никто? | «Fallback на дефолтный провайдер spacepayments» | **spacepayments — fallback по допуску, а не по исходу.** §7 |
| Есть ли одна оптимальная стратегия? | «Не существует. Задача — в рантайме подбирать наилучшие стратегии, ориентируясь на прошлые показатели» | Мета-слой выбора стратегии, §9 |
| Требования по скорости? | «Конкретных нет, просто не раздувать» | Оптимизируем читаемость, не микросекунды |

Отдельно, ответом в чат после сессии:

> Доля `traffic_percentage` считается **по итоговому `selected_provider` после fallback**.
> Горизонт — **выданная очередь**; стартовое состояние дня уже в `providers.json`;
> история — для калибровки, в знаменатель не смешивать.

## 2. Форма решения

```
$ bin/route data/operations_queue_test.json
  → routing_decisions_test.json
  → routing_report_test.json
```

Один CLI. Ни сервера, ни БД, ни фоновых задач. Состояние живёт в памяти одного процесса
и умирает вместе с ним — ровно как описали эксперты: роутер накапливает свои счётчики.

Три входа: `providers.json` (стартовый снимок), очередь операций, `operations_history.csv`
(калибровка). Два выхода — те самые файлы, которые стоят 40 баллов.

## 3. Путь одной операции

Сквозной пример на весь документ: **op_106 · 52 000 ₽ · банк sberbank**.

```
операция
   │
   ├─1─ СНИМОК          состояние провайдеров на этот момент
   ├─2─ ДОПУСК          hard-constraints → кто вообще может
   ├─3─ ВЫБОР СТРАТЕГИИ какая политика активна для этой операции
   ├─4─ РАНЖИРОВАНИЕ    стратегия строит порядок
   ├─5─ СЛОИ            мягкие сигналы двигают порядок
   ├─6─ КАСКАД          упорядоченный список кандидатов
   │
   ├─7─ РЕЗЕРВ          счётчики закрепляются за первым
   ├─8─ ПОПЫТКА         исход: approved / rejected / expired
   │      ├ approved → коммит, конец
   │      ├ rejected → откат резерва, следующий в каскаде
   │      └ expired  → резерв держится, конец (статус-чек позже)
   │
   └─9─ ЗАПИСЬ          attempts + обновление статистики
```

Для op_106 это разворачивается так:

| Стадия | Что произошло |
|---|---|
| Допуск | `payflow` отсеян: `amount_exceeds_limit`, «52 000 > limit_amount_max 50 000». Прошли `vipay`, `quickpay` |
| Ранжирование | активна count share. `vipay` недобирает 6.7 п.п. до цели 40%, `quickpay` перебирает 4.2 п.п. → порядок `vipay → quickpay` |
| Каскад | `vipay → quickpay` |
| Резерв | `vipay`: `in_progress_count 4→5`, `in_progress_amount 380 000→432 000`, счётчик долей +1 |
| Попытка | `approved` → `daily_approved 3 200 000→3 252 000`, `in_progress` освобождён, резерв доли зафиксирован |

Три границы, которые нельзя размывать:

- **Допуск отвечает «можно ли»**, стратегия — «кого предпочесть». Эксперты подтвердили,
  что конфликта между hard и soft быть не может: soft работает только внутри допущенных.
- **Роутинг строит план, исполнение его проходит.** Стратегия не знает про таймауты,
  исполнитель не знает про доли.
- **План строится до первой попытки.** После отказа мы не пересчитываем стратегию —
  идём к следующему в уже построенном каскаде.

## 4. Состояние и резервирование — сердце решения

Это прямая реализация ответа: *«закрепляем в счётчик сразу, при отказе освобождаем по всем
коэффициентам, туда может попасть другая операция»*.

```ruby
module State
  class Providers
    def reserve(provider, operation)
      p = @by_name[provider]
      p.in_progress_count  += 1
      p.in_progress_amount += operation.amount
      p.units              += @allocator.units(operation)   # доля: 1 или amount
      @reservations[[operation.id, provider]] = operation.amount
    end

    def commit(provider, operation)                          # approved
      p = @by_name[provider]
      p.daily_approved_amount += operation.amount
      release_capacity(p, operation)                         # доля остаётся
    end

    def rollback(provider, operation)                        # rejected
      p = @by_name[provider]
      p.units -= @allocator.units(operation)                 # доля возвращается
      release_capacity(p, operation)
    end

    def hold(provider, operation) = nil                      # expired: держим всё
  end
end
```

Три состояния резерва и то, что с ними происходит:

| Исход | `in_progress` | `daily_approved` | счётчик доли |
|---|---|---|---|
| `approved` | освобождается | **+ amount** | остаётся у провайдера |
| `rejected` | освобождается | не трогаем | **возвращается** |
| `expired` | держится | не трогаем | остаётся (условно) |

**Почему это важнее, чем кажется.** Механизм отката — это и есть реализация правила
«доля считается по итоговому провайдеру». Резерв ставится на кандидата, при отказе
снимается, и в конце операции счётчик доли оказывается ровно у того, кто заявку принял.
Один механизм закрывает сразу два ответа Q&A, и его не нужно дублировать отдельной
логикой пересчёта.

Два места, где легко потерять баллы молча:

- `in_progress` не освободить — и `vipay` искусственно кончится на седьмой заявке,
  eligibility поедет, эталонные кейсы валидатора упадут;
- `daily_approved` нарастить на `rejected` — и утилизация завысится, провайдер отсечётся
  раньше времени.

Оба ловятся инвариантами из §12, а не внимательностью.

## 5. Допуск: hard-constraints

Реестр независимых проверок, порядок фиксирован, каждая возвращает свой `reason`.
Названия причин взяты дословно из `reference_decisions.json` — валидатор сверяет их.

```ruby
module Routing::Constraints
  REGISTRY = [Status, TrafficShare, AmountRange, DailyLimit,
              InProgress, BankFilter, Margin, Requisites, RateLimit].freeze

  def self.check(provider, operation, state)
    REGISTRY.lazy.filter_map { |c| c.violation(provider, operation, state) }.first
  end
end
```

| Проверка | Отсев | `reason` |
|---|---|---|
| Status | `status != "active"` | `provider_inactive` |
| TrafficShare | `traffic_percentage == 0`, кроме spacepayments | `zero_traffic_share` |
| AmountRange | ниже `limit_amount_min` | `amount_below_minimum` |
| AmountRange | выше `limit_amount_max` | `amount_exceeds_limit` |
| DailyLimit | `daily_approved + amount > daily_amount_limit` | `daily_limit_exceeded` |
| InProgress | превышение count или amount | `in_progress_limit_exceeded` |
| BankFilter | не проходит `banks` / `exclude_banks` | `bank_not_in_list` |
| Margin | `provider_margin > merchant_margin` без `allow_negative_agreement` | `negative_margin` |
| Requisites | `available_requisites == 0` | `no_requisites` |
| RateLimit | превышен `requests_per_minute_limit` | `rate_limit_exceeded` |

Каждая проверка — отдельный файл с одним методом. Добавить новое ограничение = добавить
файл и строку в реестр. Это часть 5 баллов за «новые правила без переработки архитектуры».

`null` в любом лимите означает «ограничения нет» — это отдельный тест, в данных так
устроен `spacepayments`.

## 6. Аллокатор долей

Обе share-стратегии — один алгоритм с разной функцией вклада. Никакого weighted random:
случайность несовместима с воспроизводимостью, а воспроизводимость — наша главная цифра.

```ruby
class Allocator
  def units(operation)
    @mode == :count ? 1 : operation.amount
  end

  # Виртуальное время: кто дальше всех отстал от своей доли, тот первый.
  def order(candidates, state)
    candidates.sort_by { |p| Rational(state.units(p), weight_bp(p)) }
  end
end
```

Провайдер, у которого `units / weight` меньше, недополучил относительно своей цели —
он и идёт первым. Сравнение дробей делаем перекрёстным умножением целых, без float:
`u_a * w_b < u_b * w_a`. Веса — в базисных пунктах, суммой 10 000.

При равенстве — детерминированный tie-break: сначала больший вес, потом имя по алфавиту.
Никакого `rand`, `shuffle`, `sample`, `Time.now` в решающем пути.

Счётчик `units` стартует с нуля: по ответу Q&A горизонт доли — выданная очередь, история
в знаменатель не входит. При этом `daily_approved_amount` берётся из снимка — лимиты
считаются за весь день. **Две разные базы, легко перепутать.**

## 7. Каскад и исходы

```ruby
class Executor
  def run(plan, operation, state)
    plan.candidates.each do |provider|
      state.reserve(provider, operation)
      result = @outcomes.call(operation, provider, plan.attempt_no_for(provider))
      log_attempt(provider, result)

      case result
      when :approved then state.commit(provider, operation);   return done(provider, :approved)
      when :expired  then state.hold(provider, operation);     return done(provider, :expired)
      when :rejected then state.rollback(provider, operation); next
      end
    end
    done(plan.candidates.last, :rejected)      # каскад исчерпан
  end
end
```

Три исхода ведут себя по-разному, и это прямо из Q&A:

**`approved`** — коммит, каскад закончен.

**`rejected`** — провайдер отказался принять. Откат резерва, идём к следующему.
Именно здесь работает фраза экспертов «туда может попасть другая операция».

**`expired`** — таймаут, результат неизвестен. По ответу Q&A **считаем условно успешным**:
резерв держим, каскад **не продолжаем**. Позже статус-чек может вернуть отмену — тогда
освобождаем коэффициенты и применяем **компенсирующую корректировку с текущего момента**,
не пересчитывая уже принятые решения. Это `Execution::PendingResolver`, отдельный модуль.

**spacepayments — fallback по допуску, а не по исходу.** Эксперты сказали: «если hard-фильтр
не прошёл никто — fallback на spacepayments». Он подхватывает операцию, для которой не
нашлось ни одного допустимого внешнего провайдера. Он **не** подхватывает операцию, у
которой единственный допустимый провайдер отказал: тогда каскад исчерпан, операция
завершается на нём со статусом `rejected`.

Это не формальность. Если пустить spacepayments после отказа, то op_103 (единственный
допустимый — quickpay) при отказе даст `selected_provider: "spacepayments"`, и валидатор
поставит ❌ на эталонном кейсе. Плюс провайдер с нулевой целевой долей перетянул бы на
себя все безальтернативные заявки и распределение поехало бы.

### Источник исходов

Одна чистая функция, три реализации за общим интерфейсом:

```ruby
class OutcomeSource::Deterministic
  def call(operation, provider, attempt_no)
    roll = Digest::SHA256
      .hexdigest("#{@seed}:#{operation.id}:#{provider}:#{attempt_no}")
      .to_i(16) % 10_000
    threshold = (@conversions.fetch(provider) * 10_000).round
    return :approved if roll < threshold
    roll < threshold + @reject_share ? :rejected : :expired
  end
end
```

| Реализация | Где применяется |
|---|---|
| `Deterministic` | боевой прогон: хеш против калиброванной конверсии |
| `Scripted` | тесты и демо: YAML вида «vipay отказывает на op_101» |
| `AlwaysOk` / `AlwaysFail` | вырожденные случаи каскада в тестах |

Конверсии берутся не из `conversion_24h`, а калибруются по `operations_history.csv` —
паспортные цифры расходятся с фактом почти вдвое (§11).

## 8. Семь стратегий

Каждая — отдельный класс с одним методом. Стратегия **упорядочивает**, а не выбирает:
первый в списке — выбор, весь список — каскад.

```ruby
Strategy#rank(candidates, operation, state) -> [Provider]
```

| # | Класс | Механика | Балл |
|---|---|---|---|
| 1 | `CountShare` | аллокатор, `units = 1`, цель `traffic_percentage` | 3 |
| 2 | `VolumeShare` | аллокатор, `units = amount`, цель `volume_share_pct` | 3 |
| 3 | `Priority` | по возрастанию `priority` | 3 |
| 4 | `AmountRange` | правила `500–50 000 → payflow` **влияют на порядок**, не только фильтруют | 3 |
| 5 | `Conversion` | по наблюдаемой конверсии, убыванием | 3 |
| 6 | `Load` | по возрастанию `in_progress / in_progress_limit` | 3 |
| 7 | `Obligations` | `daily_turnover_min` не набран → вверх; близко к max → вниз | 3 |

Стратегии 4 и 6 жюри оговаривает отдельно: диапазон суммы и загрузка должны влиять на
ранжирование, а не быть только ограничением. Поэтому обе живут и в `constraints/`
(как жёсткий отсев), и в `strategies/` (как предпочтение) — это разные вещи.

### Слои — мягкие модификаторы

Поверх базовой стратегии включаются независимые слои, каждый двигает порядок:

```
допущенные → [базовая стратегия] → [conversion] → [load] → [obligations] → каскад
```

Единственный инвариант, который нельзя нарушать: **слой не может вернуть в список того,
кого отсёк допуск**. Он только переставляет. Это ровно то, что эксперты имели в виду,
говоря «конфликта между hard и soft быть не может».

## 9. Выбор стратегии в рантайме

Эксперт сказал прямо: *«задача не конкретный набор тестовых данных заработать, а уметь в
рантайме подбирать наилучшие стратегии и ориентироваться на показатели, которые уже были
в прошлом»*. Отвечаем правилами, а не обучением.

```yaml
strategy_selection:
  default: count_share
  rules:
    - when: { amount_gte: 100000 }
      use: volume_share
      why: "крупная операция сильнее влияет на денежное распределение"
    - when: { observed_conversion_below: 0.5, provider_share_of_queue_gte: 0.3 }
      use: conversion
      why: "доминирующий провайдер деградировал — временно приоритезируем успешность"
```

Правило, которое сработало, попадает в `attempts` вместе с причиной. Судья видит не
«движок решил», а «правило №2 сработало, потому что наблюдаемая конверсия 0.47 < 0.5».

Это закрывает 7 баллов за «формализованный способ совместного учёта факторов» и
одновременно — просьбу эксперта про рантайм-подбор, без единой строчки ML.

## 10. Согласование конфликтов

Ситуация из ТЗ: цель 40% на vipay, но vipay почти исчерпал дневной максимум, а на payflow
висит обязательство «не менее 2 млн ₽/сутки».

Три правила разрешения, все три проговариваются на защите:

**1. Приоритет политик задан явно в конфиге**, а не выведен из весов. При конфликте
побеждает слой, стоящий выше в списке. Срабатывание пишется в `attempts` с числами.

**2. Недостижимая цель перенормируется.** Если провайдер недопустим для данной операции,
его доля перераспределяется между допущенными пропорционально их весам. Отклонение
меряется от **достижимой** доли, а не от паспортной.

**3. Разница между целью и достижимым идёт в отчёт как отдельная величина**, а не
маскируется. Это прямо закрывает 4 балла за «поведение системы, если цель выполнить
невозможно».

Пример на public-очереди из 10 заявок. Банковские фильтры и лимиты сумм жёстко
предопределяют часть маршрутов:

| | target | achievable | почему |
|---|---|---|---|
| vipay | 40% | 40% | op_101, 105, 106, 109 |
| payflow | 35% | **30%** | доступны 4 заявки, но headroom 100 000 ₽ хватает на 3 |
| quickpay | 25% | **30%** | op_103, 104, 108 — больше некому |

Максимальное отклонение 5 п.п. — это **арифметический пол, а не наш промах**: на десяти
заявках доля квантуется шагом 10 п.п., в 35% попасть невозможно в принципе. Если движок
выдаёт ровно 40/30/30, он отработал идеально, и отчёт обязан это объяснить числами.

## 11. Объяснимость

Формат жёстко ограничен валидатором: `decision` принимает только `selected` и `skipped`,
всё остальное — ошибка структуры. Неудачная попытка кодируется как `selected` плюс наши
дополнительные поля (ТЗ разрешает их добавлять).

```json
{
  "operation_id": "op_106",
  "selected_provider": "vipay",
  "attempts": [
    {"provider": "payflow", "decision": "skipped",
     "reason": "amount_exceeds_limit", "details": "52000 > limit_amount_max 50000"},
    {"provider": "vipay", "decision": "selected",
     "reason": "best_target_adherence", "attempt_no": 1, "result": "approved",
     "details": "недобор доли 6.7 п.п. против перебора quickpay 4.2 п.п.",
     "strategy": "count_share"}
  ],
  "simulated_result": "approved",
  "latency_sec": 38
}
```

Правило команды: **причина без числа не принимается.** `details` всегда содержит конкретное
сравнение. Порядок элементов = порядок рассмотрения, включая повторные попытки — это
2 балла за «сохранена последовательность рассмотрения».

В `attempts` попадают **все** рассмотренные провайдеры, а не только выбранный. Отсев —
это половина объяснимости и 9 баллов из 25.

## 12. Отчёт и аналитика

Обязательные поля из ТЗ плюс наши расширения:

```json
{
  "period": "2026-07-30",
  "total_operations": 10,
  "strategy": "count_share",
  "distribution": {
    "vipay": {"count": 4, "share_pct": 40.0, "target_pct": 40,
              "achievable_pct": 40.0, "deviation_pp": 0.0}
  },
  "volume_distribution": { },
  "attempt_distribution": { },
  "skip_reasons": {"amount_exceeds_limit": 3, "bank_not_in_list": 5},
  "projected_daily_utilization": {
    "payflow": {"used": 2988800, "limit": 3000000, "utilization_pct": 99.6}
  },
  "fallback": {"first_attempt_success": 8, "recovered_by_fallback": 1,
               "fallback_rate_pct": 20.0, "spacepayments_used": 0},
  "deviation_causes": [
    "quickpay +5 п.п.: op_103, op_104, op_108 не имели альтернатив по сумме и банку"
  ],
  "recommendations": [
    "payflow: conversion_24h заявлена 0.91, наблюдаемая 0.47 — пересчитать по факту",
    "payflow: свободно 100 000 ₽ при среднем чеке 38 580 ₽ — снизить traffic_percentage 35 → 20 до сброса дневного лимита"
  ]
}
```

Три распределения считаются раздельно и отвечают на разные вопросы:

| | Считает | Зачем |
|---|---|---|
| `distribution` | по итоговому `selected_provider` | **официальная** доля против цели, по ответу Q&A |
| `attempt_distribution` | все реальные попытки | фактическая нагрузка на провайдера |
| `volume_distribution` | итоговый провайдер, вес — сумма | цель `volume_share_pct` |

Наблюдаемая конверсия считается как `successful / attempts` — без разделения на три
распределения она посчиталась бы неправильно.

**Калибровка по истории.** Разбор `operations_history.csv` даёт готовый вывод:

| | доля count | approved по факту | заявлено `conversion_24h` |
|---|---|---|---|
| vipay | 41% | **78.0%** | 0.87 |
| payflow | 19% | **47.4%** | 0.91 |
| quickpay | 40% | **67.5%** | 0.79 |

Паспортные конверсии недостоверны, payflow вдвое хуже заявленного и недобирает 16 п.п.
до целевой доли. Это конкретная параметрическая рекомендация — 2 балла.

### Блок `benchmark`: почему `offline_bound`, а не `offline_optimum`

Эталон для сравнения (X-4, X-5) считается **постфактум**, когда очередь и все исходы уже
известны. Контрфактуалы — «что было бы при другом маршруте» — вычислимы, потому что исход
это чистая функция от `(seed, operation_id, provider, attempt_no)` (§7), а не бросок кубика.
Оракул находится вне решающего пути и вправе их считать.

Но точным оптимумом результат назвать нельзя, и поле в отчёте это отражает:

```json
"benchmark": {
  "offline_bound": {"max_deviation_pp": 5.0, "delivered": 10},
  "our_online_result": {"max_deviation_pp": 5.0, "delivered": 10},
  "competitive_ratio": 1.0,
  "note": "эталон эвристический: перебор с учётом порядка, не доказанный оптимум"
}
```

Причина в том, что задача **не разваливается на независимые назначения**: одобрение съедает
`daily_amount_limit` и `in_progress`, меняя допуск для последующих заявок. Значит перебирать
надо назначения с учётом порядка, а жадный поиск с локальными улучшениями даёт нижнюю
оценку, а не доказанный минимум. Называть её оптимумом — обещать больше, чем считаем.

Полный разбор и обязательные требования к постановке — `TASKS.md`, фаза Ф5,
«Три оговорки к X-4/X-5».

## 14. Конфигурация

Один YAML определяет всё поведение. Смена стратегии, порогов, правил и лимитов —
**без правки кода**, это 6 баллов.

```yaml
strategy: count_share
layers: [conversion, load, obligations]        # порядок = приоритет при конфликте
allocator: { tie_break: [weight_desc, name_asc] }
outcomes: { source: deterministic, seed: 42, calibrate_from_history: true }
amount_ranges:
  - { from: 500,    to: 50000,  prefer: payflow }
  - { from: 50001,  to: 100000, prefer: vipay }
  - { from: 100001, to: null,   prefer: quickpay }
obligations:
  payflow: { daily_turnover_min: 2000000 }
  vipay:   { daily_turnover_max: 5000000 }
rate_limits: { vipay: 7, quickpay: 15 }
fallback_provider: spacepayments
```

Новый провайдер — строка в `providers.json`. Новое правило — файл плюс строка в конфиге.
Ни то, ни другое не требует трогать существующий код: 5 баллов за расширяемость.

## 15. Тесты и инварианты

Пять сценариев каскада:

| Сценарий | Ожидание |
|---|---|
| Первый успешен | одна попытка, `daily_approved` вырос только у него |
| Отказ → следующий успешен | две попытки, резерв первого откачен полностью |
| Таймаут | резерв держится, каскад не продолжается |
| Каскад исчерпан | `selected_provider` — последний реальный, не spacepayments |
| Никто не прошёл допуск | `selected_provider` — spacepayments |

Инварианты, проверяемые на **каждом** прогоне, а не отдельным тестом:

```ruby
expect(attempts.map(&:provider).uniq.size).to eq attempts.size     # без дублей
expect(state.in_progress_count).to eq initial_in_progress          # всё освобождено
expect(skipped.map(&:reason)).to all be_in(Constraints::REASONS)
expect(selected_provider).to be_in eligible_from_snapshot          # правило валидатора
expect(run_twice.map(&:to_json).uniq.size).to eq 1                 # воспроизводимость
```

Предпоследний воспроизводит логику `validate_10.rb` внутри нашего сьюта — проблема
находится на своём прогоне, а не за час до стопкода. `rake validate` на public-очереди —
условие мержа в `main`.

Отдельный греп в CI на `rand|shuffle|sample|Time\.now` в `lib/routing` и `lib/execution`.

## 16. Граничные случаи

5 баллов за «обработка ошибок и граничных ситуаций» — это конкретный список, а не
общее качество кода:

| Случай | Поведение |
|---|---|
| `null` в любом лимите | ограничения нет (так устроен spacepayments) |
| Неизвестный банк | проходят только провайдеры с пустым `banks` |
| Пустой `banks` | принимает все банки |
| `exclude_banks: true` | список работает как чёрный |
| Сумма ≤ 0, нет обязательного поля | операция отклоняется с явной причиной, прогон продолжается |
| Дубль `operation_id` | предупреждение, первое решение сохраняется |
| Пустая очередь | валидные файлы с нулями, не падение |
| Ни одного активного провайдера | всё уходит в spacepayments |
| Провайдер в очереди, но не в `providers.json` | падение на загрузке с внятным сообщением |

## 17. Чего в архитектуре нет

БД, Redis, очередей, HTTP-сервера, дашборда, ML и нейросетей, DSL правил, микросервисов,
look-ahead-оптимизации по всей очереди, единого композитного «умного скоринга»,
многопоточности, авторизации.

Первые три отменены прямым ответом экспертов «критерии это никак не вознаграждают».
Look-ahead — ответом «каждая операция получает свой снимок». Нейросети — ограничением ТЗ.
Композитный скоринг — тем, что объяснимость стоит 25 баллов, а необъяснимое число их не даёт.
